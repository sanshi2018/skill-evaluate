## 2. 与既有 `ExecutorBackend` 抽象的关系：引入 `ScriptSandboxRunner`

本维度的核心操作是"直接裸调脚本子进程并检查其行为"，**不涉及 LLM 驱动的 Agent 执行循环**——没有 `thought`、没有工具调用轨迹，只有一次确定性的子进程调用。这与文档 03 `ExecutorBackend`（面向"Agent 执行一个任务，产出完整 Trace"）在语义上不同，本文档不强行复用 `ExecutorBackend` 接口，而是新增一个平行的轻量组件：

```python
# src/skill_evaluate/executors/script_sandbox.py
class ProcessResult(BaseModel):
    exit_code: int | None          # None 表示超时被杀
    stdout: str
    stderr: str
    timed_out: bool
    duration_ms: int


class ScriptSandboxRunner:
    """复用文档03同款 Ephemeral Docker 安全约定（无出站网络、Wall-clock超时），
    但只执行一条命令并直接返回子进程结果，不接入 Hermes/LLM 推理循环。
    与 ExecutorBackend 是同级但不同用途的两个执行组件，均落在 executors/ 包下。"""

    async def run(
        self, image: str, command: list[str], stdin_data: bytes | None = None,
        cwd: str | None = None, timeout_s: int = 10,
    ) -> ProcessResult:
        """以无 TTY 方式启动子进程（避免继承任何交互终端），
        timeout_s 到期后发送 SIGKILL 并标记 timed_out=True。"""
```

沙箱镜像 `image` 默认使用与被测 Skill 语言匹配的最小运行时镜像（`python:3.13-slim` / `node:22-slim` / `bash:5` 等，由脚本文件扩展名或 shebang 推断，推断逻辑放在 `script_sandbox.py` 的 `infer_runtime_image()`）。输出统一经过文档 03 第 8 节同款的截断工具处理。

## 4. `hard_failure_probing`：非交互性挂起测试

```python
async def hard_failure_probing(state: PipelineState) -> PipelineState:
    findings = []
    for script in state["_scripts"]:
        result = await script_sandbox.run(
            image=infer_runtime_image(script.path),
            command=[interpreter_for(script.path), script.path],   # 故意不传任何参数
            stdin_data=b"",                                          # 空 stdin，模拟无交互输入
            timeout_s=10,
        )
        if result.timed_out:
            findings.append(f"[致命] {script.path} 在缺失参数时挂起超过10秒未退出，判定为非交互性失败")
    return {**state, "_hard_failure_findings": findings}
```

`timeout_s=10` 是本文档为"挂起探测"设定的专用短超时（区别于常规 Hermes 执行的 60 秒沙箱超时）——挂起测试的本意就是"脚本应该立刻拒绝或报错，不应该等待任何输入"，10 秒已经是相当宽松的容忍窗口。命中挂起直接判定为 **Fatal（阻断）**，不经过 Mini Agent 复核——"是否挂起"是二元确定性事实，不需要语义裁决。

## 5. `self_learning_doc_test`：`--help` 文档质量审查

```python
async def self_learning_doc_test(state: PipelineState) -> PipelineState:
    verdicts = []
    for script in state["_scripts"]:
        result = await script_sandbox.run(
            image=infer_runtime_image(script.path),
            command=[interpreter_for(script.path), script.path, "--help"],
            timeout_s=10,
        )
        help_text = result.stdout or result.stderr   # 有的脚本习惯把help输出到stderr，两者都接受
        v = await judge_agent.judgmental_verdict(
            subject_id=script.path, template_key="help_doc_quality",   # 文档07模板5.4
            content={"help_output": help_text}, criticality=Criticality.ROUTINE,
        )
        verdicts.append(v)
    return {**state, "judge_verdict_ids": [v.verdict_id for v in verdicts], "_help_verdicts": verdicts}
```

若脚本对 `--help` 也没有实现（`exit_code != 0` 且输出为空），本文档约定：直接构造一个 `status=FAIL` 的 `JudgeVerdict`（不调用 LLM，空输入没有审查价值），`reasoning="脚本未响应 --help 标志"`。

## 6. `constructive_error_and_io_separation_test`：脏数据与流隔离

```python
async def constructive_error_and_io_separation_test(state: PipelineState) -> PipelineState:
    verdicts = []
    for script in state["_scripts"]:
        dirty_input = generate_dirty_payload(script)   # 见6.1
        result = await script_sandbox.run(
            image=infer_runtime_image(script.path),
            command=[interpreter_for(script.path), script.path, "--input", dirty_input.arg_value],
            timeout_s=15,
        )
        io_separation_ok = _check_io_separation(result)   # 见6.2，纯代码检查
        v = await judge_agent.judgmental_verdict(
            subject_id=script.path, template_key="constructive_error",   # 文档07模板5.5
            content={"stderr": result.stderr, "stdout": result.stdout, "exit_code": result.exit_code},
            criticality=Criticality.ROUTINE,
        )
        verdicts.append((v, io_separation_ok))
    return {**state, "_constructive_error_results": verdicts}
```

### 6.2 流隔离的确定性检查

```python
def _check_io_separation(result: ProcessResult) -> bool:
    """纯代码检查：exit_code != 0 时，stdout 不应包含明显的错误/异常堆栈特征
    （正则匹配常见 Traceback/Error 关键词），这些应该出现在 stderr。
    这是一个启发式规则，不追求 100% 准确，作为 Mini Agent 语义审查（6节主体）的补充信号，
    而非独立判定依据——两者共同出现在报告中，最终判定以 Mini Agent 的 constructive_error verdict 为准。"""
```

## 7. `idempotency_and_safety_guards`：幂等性与输出截断

```python
async def idempotency_and_safety_guards(state: PipelineState) -> PipelineState:
    findings = []
    for script in state["_scripts"]:
        if not is_mutating_script(script):   # 简单启发式：脚本描述/参数中含 write/create/update 等词
            continue
        first = await script_sandbox.run(image=..., command=_mutating_invocation(script), timeout_s=15)
        second = await script_sandbox.run(image=..., command=_mutating_invocation(script), timeout_s=15)
        if second.exit_code not in (0,) and _looks_like_unhandled_crash(second.stderr):
            findings.append(f"[阻断] {script.path} 连续两次执行导致未处理崩溃（'状态已存在'场景未被妥善处理）")

        for r, label in [(first, "first"), (second, "second")]:
            if len(r.stdout) + len(r.stderr) > OUTPUT_TRUNCATION_WARN_BYTES:   # 默认32KB，与文档03截断阈值对齐
                findings.append(f"[警告] {script.path} 第{label}次执行输出超过防刷屏建议上限，未见截断标记")
    return {**state, "_idempotency_findings": findings}
```

`is_mutating_script()` / `_mutating_invocation()` 的具体启发式规则依赖 `SkillScript` 的元数据（文档 02 当前字段较简单，本文档追加 `SkillScript.is_mutating: bool | None` 字段，由 `skill_loader.py` 解析脚本内容中的常见写操作 API 调用做启发式标注，解析失败则为 `None`，`None` 时本节点跳过该脚本的幂等性测试并在报告中标注"无法自动判定是否为突变脚本，建议人工确认"）。

## 8. 报告聚合

```python
async def finalize_dimension_report(state: PipelineState) -> PipelineState:
    fatal = state["_hard_failure_findings"]
    idempotency_blocking = [f for f in state["_idempotency_findings"] if f.startswith("[阻断]")]
    warnings = [
        *[f for f in state["_idempotency_findings"] if f.startswith("[警告]")],
        *[v.reasoning[:200] for v in state["_help_verdicts"] if v.status == JudgeVerdictStatus.FAIL],
        *[v.reasoning[:200] for v, _ in state["_constructive_error_results"] if v.status == JudgeVerdictStatus.FAIL],
    ]
    blocking = bool(fatal or idempotency_blocking)
    await report_generator.record_dimension_result(
        run_id=state["run_id"],
        result=DimensionResult(
            dimension="script_usability",
            status=JudgeVerdictStatus.FAIL if (blocking or warnings) else JudgeVerdictStatus.PASS,
            score=None,
            findings=[*fatal, *idempotency_blocking, *warnings],
            blocking=blocking,   # 挂起(Fatal)与幂等性崩溃阻断；Help文档质量/建设性报错/输出截断仅告警
        ),
    )
    return state
```

**阻断策略延续文档 12/13 的一贯原则**：能被确定性验证的安全/可用性硬伤（挂起、崩溃）阻断合并；依赖 LLM 主观审查的"文档写得好不好""报错够不够建设性"只告警，理由同前——避免主观审查误报直接拖垮流水线可信度。
