## 3. `extract_tier_and_negative_constraints`：补全 Analyzer Agent

对文档 16 `AnalyzerAgent.extract_capability_tree()` 的**追加子任务**（不是新建方法，是对已有方法内部逻辑的补全——文档 16 定义该方法时已声明"tier 占位、negative_constraints 留空"是阶段性状态，本文档正式交付完整实现）：

```python
# 对 agents/analyzer/service.py 的补全
class AnalyzerAgent(BaseLLMAgent):
    async def classify_tiers(self, tree: CapabilityTree, skill: SkillDefinition) -> CapabilityTree:
        """针对tree中每个capability_id，让LLM判定其属于P0(核心路径)/P1(条件分支)/P2(防御与格式)。
        Prompt要求：P0对应"如果这项能力失效，Skill基本等同于不可用"；
        P1对应"特定条件下才触发的分支能力"；P2对应"格式规范/降级/边界修饰类能力"。
        采用few-shot示例（文档08.4权衡分析建议的"标准能力与权重拆解范本"）固化判定标准，
        减少模型自由发挥导致的分级不一致。原地更新tree.nodes[i].tier，capability_id不变。"""

    async def extract_negative_constraints(self, skill: SkillDefinition) -> list[NegativeConstraint]:
        """扫描skill.body_markdown中的"Gotchas/避坑指南"类段落（可通过标题关键词如
        "Gotchas"/"注意"/"避免"/"Common Mistakes"辅助定位，但不强制要求特定标题——
        Prompt要求模型识别任何形式的"负向约束"表述，即"必须避免/不能/禁止做某事"的陈述句，
        与常识剥离度审计(文档07模板5.1)的判定逻辑有相似之处但目标相反：
        omission_audit找的是"该删的常识"，这里找的是"该保留且必须被测试覆盖的禁止性规则"，
        两者不合并为一个模板，因为一个是删减建议、一个是覆盖率追踪对象，用途不同。"""
```

`NegativeConstraint.constraint_id` 同样采用文档 16 第 2.1 节的确定性哈希方案，保证跨版本稳定性。

```python
async def extract_tier_and_negative_constraints_node(state: PipelineState) -> PipelineState:
    tree = await capability_repository.get(state["capability_tree_id"])
    skill = await skill_repository.get(state["skill_id"], state["skill_version_ref"])
    tree = await analyzer_agent.classify_tiers(tree, skill)
    tree.negative_constraints = await analyzer_agent.extract_negative_constraints(skill)
    await capability_repository.save(tree)
    return state
```

## 4. `map_negative_constraint_coverage`：对抗性用例映射

```python
async def map_negative_constraint_coverage(state: PipelineState) -> PipelineState:
    tree = await capability_repository.get(state["capability_tree_id"])
    cases = await test_case_repository.list_by_categories(
        state["active_suite_version_id"], [TestCaseCategory.POSITIVE, TestCaseCategory.ADVERSARIAL]
    )   # 既扫常规正向用例(可能碰巧诱导了陷阱)，也扫模块五的对抗用例(更可能专门设计诱导陷阱)
    for constraint in tree.negative_constraints:
        covering = [
            c.case_id for c in cases
            if await analyzer_agent.does_case_probe_constraint(c, constraint)   # 见4.1
        ]
        constraint.covered = bool(covering)
        constraint.covering_case_ids = covering
    await capability_repository.save(tree)
    uncovered = [c.constraint_id for c in tree.negative_constraints if not c.covered]
    return {**state, "_uncovered_constraint_ids": uncovered}
```

### 4.1 `does_case_probe_constraint`

```python
async def does_case_probe_constraint(self, case: TestCase, constraint: NegativeConstraint) -> bool:
    """判定某用例是否"故意诱导踩坑"——例如约束是"查询users表须加WHERE deleted_at IS NULL"，
    用例需要构造出"数据中存在软删除记录"的场景才算真正测试了这条约束(而不仅仅是普通查询)。
    这是结构化布尔判定，走Judge Agent的judgmental_verdict（Criticality.ROUTINE——
    误判的后果是"漏标一个未覆盖约束"，属于覆盖率统计场景而非阻断合并的重大判决，
    不需要CRITICAL级别的共识投票，与本文档整体"覆盖率不阻断"的基调一致）。"""
```

**未覆盖的负向约束** 通过 `CapabilityFocus.negative_constraint_ids`（文档 06 定义、此前一直待接入，本文档正式落地）反向驱动 Generator：Generator 收到该字段后，需要在文档 06 第 5.1 节正向用例 Prompt 模板中新增一段"针对指定约束构造反事实场景"的指令分支（对文档 06 Prompt 内容的一次充实，不改变 `GenerationRequest`/`incremental_patch` 的接口结构）。

## 5. `recompute_weighted_coverage`：替换文档 16 占位规则

```python
def weighted_capability_coverage(inputs: dict) -> JudgeVerdictStatus:
    tree: CapabilityTree = inputs["tree"]
    ratio = tree.weighted_coverage()   # 文档02已实现的方法：sum(covered*weight)/sum(weight)
    return JudgeVerdictStatus.PASS if ratio >= inputs["threshold"] else JudgeVerdictStatus.FAIL

# 覆盖(而非新注册)文档16的规则实现体，规则名"capability_coverage_threshold"保持不变
override_rule("capability_coverage_threshold", weighted_capability_coverage)
```

`judge/rules.py` 的注册表本文档新增 `override_rule()`（区别于 `register_rule()`）——语义上明确"这是替换已存在的规则实现"而非"注册一个新规则"，避免同名重复注册被静默覆盖时难以察觉是有意为之还是 bug（`register_rule()` 若发现同名 key 已存在应直接抛错，这是本文档对文档 08 `judge/rules.py` 注册机制的一处补充约定）。文档 16 的调用方节点（`blind_spot_detection`）代码不需要任何修改——它调用的是规则名字符串 `"capability_coverage_threshold"`，实现体的替换对它透明。

## 6. `upgrade_combinatorial_priority`：替换文档 17 过渡截断策略

```python
def prioritized_uncovered_pairs(tree: CapabilityTree, uncovered_pairs: list[tuple[str, str]], limit: int) -> list[tuple[str, str]]:
    def pair_priority(pair: tuple[str, str]) -> float:
        tier_a = next(n.tier for n in tree.nodes if n.capability_id == pair[0])
        tier_b = next(n.tier for n in tree.nodes if n.capability_id == pair[1])
        return TIER_WEIGHTS[tier_a] + TIER_WEIGHTS[tier_b]   # P0×P0组合优先级最高(1.2)，P2×P2最低(0.2)

    return sorted(uncovered_pairs, key=pair_priority, reverse=True)[:limit]
```

文档 17 第 5 节的过渡逻辑（简单截断取前 N 个）由本函数替换调用；`combinatorial_matrix_analysis` 节点内部对 `state["_uncovered_pairs"]` 排序时改为调用 `prioritized_uncovered_pairs()`，这是本文档对文档 17 节点内部实现的一处正式升级说明（同样不改变文档 17 已确认的接口/数据结构）。

## 7. `generate_traceability_artifact`：可追溯性热力图制品

```python
async def generate_traceability_artifact(state: PipelineState) -> PipelineState:
    tree = await capability_repository.get(state["capability_tree_id"])
    matrix_json = {
        "skill_id": tree.skill_id, "skill_version_ref": tree.skill_version_ref,
        "generated_at": utcnow().isoformat(),
        "nodes": [
            {"id": n.capability_id, "tier": n.tier, "weight": TIER_WEIGHTS[n.tier],
             "covered": n.covered, "covering_cases": n.covering_case_ids}
            for n in tree.nodes
        ],
        "negative_constraints": [
            {"id": c.constraint_id, "covered": c.covered, "covering_cases": c.covering_case_ids}
            for c in tree.negative_constraints
        ],
        "combinatorial_coverage": {
            "covered_pairs": tree.combinatorial_pairs_covered,
            "weighted_coverage_ratio": tree.weighted_coverage(),
        },
    }
    out_path = f"artifacts/{state['run_id']}/traceability_matrix.json"
    write_json(out_path, matrix_json)
    write_csv(out_path.replace(".json", ".csv"), _flatten_for_csv(matrix_json))   # 便于 diff 视图/表格工具打开
    return {**state, "_traceability_artifact_path": out_path}
```

这两份制品与文档 05 的 `benchmark.json`/HTML 走**同一套 CI 归档机制**（本文档不新建归档管道，复用文档 05 已定义的制品上传方式，文档 24 落地时统一配置）。JSON/CSV 双格式的原因：JSON 供程序化 diff（如未来接入的自动化漂移告警），CSV 供直接拖入表格工具人工审阅——两种消费场景并存，不用单一格式强行兼顾。

**Base44 热力图控制台**是架构文档提到的可视化增强层，本文档明确其为**可选的外部对接**：本文档只保证 `traceability_matrix.json` 的 schema 稳定、语义自洽、可被任意下游可视化工具消费，不在本项目代码库内实现 Base44 集成本身（Base44 是第三方低代码平台，接入细节超出本项目职责边界，若团队后续需要，属于独立的运维/前端配置任务，不产生新的开发文档编号）。
