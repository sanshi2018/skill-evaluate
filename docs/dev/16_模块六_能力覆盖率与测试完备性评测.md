## 1. 本文档目标

引入 **Analyzer Agent**，实现"声明能力拆解 → 用例-能力双向追溯 → 盲区侦测 → 反向驱动 Generator 定向补盲区"的闭环。本文档产出的 `CapabilityTree` 是模块七/八的共同基础，但本文档**只处理"是否覆盖"这一二元问题**，不处理权重分级（模块八）和组合矩阵（模块七）——三份文档共享同一棵树，各自负责不同的分析维度，避免职责混叠。

## 2. Analyzer Agent

```python
# src/skill_evaluate/agents/analyzer/service.py
class AnalyzerAgent(BaseLLMAgent):
    async def extract_capability_tree(self, skill: SkillDefinition) -> CapabilityTree:
        """通读 SKILL.md description + 正文，拆解为原子能力清单。
        本文档阶段：tier 字段统一填充占位值 CapabilityTier.P1_CONDITIONAL（不做真实分级），
        negative_constraints 留空列表——两者都是文档18的职责，此处只是保证 CapabilityTree
        实例在结构上合法可用，不代表这些字段已有意义的取值。文档18接入时会重跑一次
        extract_capability_tree的分级子任务并原地更新tier字段，不改变capability_id的稳定性
        （capability_id需要在两次抽取间保持稳定，见2.1）。"""

    async def map_case_to_capabilities(self, case: TestCase, tree: CapabilityTree) -> list[str]:
        """给定一条测试用例的prompt，判断它实际激活了树中哪些capability_id。
        这是结构化抽取任务而非pass/fail裁决，因此不经过Judge Agent的judgmental_verdict
        （那是为二元/分级判决设计的），而是Analyzer Agent自己的直接LLM调用+结构化解析，
        复用BaseLLMAgent._call_llm()但不落JudgeVerdict——落库为case.target_capability_ids
        （文档02 TestCase已有此字段，本文档是其首个真实写入方）。"""
```

**实现期的四处修订（以代码为准）**：

1. 代码落在 `src/skill_evaluate/agents/analyzer/` 下的四个文件而不是单一 `service.py`：`identity.py`（`capability_id` 的确定性生成与解析）、`schema.py`（两个任务的 LLM 输出契约）、`prompts/`（两份 Jinja 模板）、`service.py`（`AnalyzerAgent` 本体）。拆开的理由是 `identity.py` 会被文档 17/18 直接引用（`build_capability_id()` 是它们保持历史绑定不失效的前提），埋在 `service.py` 里等于要求它们导入一个 Agent 才能算一个哈希。

2. **LLM 不产出 `capability_id`，也看不到 `tier`/`covered` 字段**。模型交回的是 `ExtractedCapability{description, evidence_quote}`，id 由代码按 2.1 的哈希方案生成，`tier` 由代码填占位值。让模型自己编 id 会在第二次抽取时全部变掉，正是 2.1 要防的事。

3. **抽取结果按 `capability_id` 去重**。Prompt 已经要求"不要把同一件事换个说法写两遍"，但书写差异（标点、全角半角、大小写）本来就会被归一掉，因此"两条描述只差一个逗号"必然撞同一个 id。不去重的后果是 `CapabilityTree.nodes` 里出现两个同 id 节点：覆盖率分母被虚增，且其中一份永远标不上 `covered`——表现为一项永远补不满的盲区。

4. `evidence_quote`（要求模型逐字引用 SKILL.md 原文）是实现期新增的字段，作用有两个：抑制模型把"它大概也能做 X"写成一项声明能力；给第 4 节的人工审核卡片一个比抽象描述更快判断的依据。它**不进** `CapabilityNode`（字段表由文档 02 定，本文档不擅自扩展），而是逐条落结构化日志 `analyzer_capability_extracted`。

### 2.1 `capability_id` 的稳定性

`capability_id` 采用"基于能力描述文本的确定性哈希 + skill_id 前缀"生成（而非自增序号），保证同一份 `SKILL.md` 多次重新抽取（如文档 18 补充分级时）时，未变化的能力条目 `capability_id` 保持不变——这对第 4 节的追溯矩阵和文档 17 的孤儿用例检测都是必要前提：如果每次抽取都重新生成 ID，`TestCase.target_capability_ids` 中记录的历史绑定就会全部失效。

## 3. 子图节点序列

```
extract_capability_tree（Analyzer Agent）
      ↓
   [能力节点数超过阈值?] --是--> suspend_for_human_review（人工确认后继续）
      ↓否
map_case_coverage（对现存全部用例做能力映射）
      ↓
blind_spot_detection（纯代码：计算未覆盖节点）
      ↓
   [存在盲区 且 未达最大补盲迭代次数?] --是--> feedback_driven_generation --> map_case_coverage（回环）
      ↓否
finalize_dimension_report
```

节点名前缀：`coverage.*`（本文档、17、18 共用同一维度键 `coverage_analysis`，见文档 03 路由表，三份文档的节点在文档 24 主图装配时会被组织为同一个大的 `coverage` 子图分区，本文档只负责其中"能力提取与盲区补全"这一段）。

**实现期的四处修订（以代码为准）**：

1. **`suspend_for_human_review` 不是独立节点**，而是 `extract_capability_tree` 内部的一次 `suspend_and_wait()`（动态 `interrupt()`）。做成独立节点意味着"要不要挂起"得先落进状态再由条件边读出来，而这个判断只是一行 `len(tree.nodes) > threshold`；更要紧的是挂起点必须与产生能力树的那次调用在同一个节点里，否则恢复时重跑的是一个空转的判断节点，而人要确认的那棵树已经落库、无从复核。

2. **三个名字必须分开**：后端路由键 `coverage_analysis`（模块六/七/八共用）、图节点前缀 `coverage`（共用）、报告维度名 `capability_coverage`（**本文档独有**）。前两个按本节原意共用；第三个不能共用——`dimension_results` 的唯一约束是 `(run_id, dimension)`，三份文档若都写 `coverage_analysis`，后跑完的那个会把先跑完的整行覆盖掉，报告里只剩一个维度且没有任何报错。三个常量在 `nodes/coverage/state.py`，文档 17/18 请各自取新的 `DIMENSION` 值。

3. **环有两道出口，不是一道**。本节流程图只画了 `blind_spot_detection` 后的那道条件路由；实现里 `feedback_driven_generation` 之后还有第二道。理由是该节点自己也会把状态标成"补盲耗尽"（迭代上限的防御性检查、`incremental_patch()` 抛 `GenerationError` 的降级），此时若无条件回边，就会走回映射 → 盲区依旧 → 再来一轮，而迭代计数因为补盲失败并没有增加——那正是本文档第 7 节要防的"无限重试死锁"。

4. **本维度是全项目唯一一张带环的子图**，文档 24 编译主图时需要显式调大 `recursion_limit`（本维度最坏约 14 个超步，十个维度叠加后 LangGraph 默认的 25 很可能不够）。

## 4. `extract_capability_tree` 与人工审核卡片

```python
async def extract_capability_tree_node(state: PipelineState) -> PipelineState:
    skill = await skill_repository.get(state["skill_id"], state["skill_version_ref"])
    tree = await analyzer_agent.extract_capability_tree(skill)
    await capability_repository.save(tree)

    if len(tree.nodes) > settings.coverage.capability_count_review_threshold:   # 新增配置，默认20
        await suspend_and_wait(
            reason=f"capability_tree_size_exceeds_threshold:{len(tree.nodes)}",
            wait_key=f"{state['run_id']}:coverage:tree_review",
        )
    return {**state, "capability_tree_id": tree.skill_id + ":" + tree.skill_version_ref}
```

这一挂起点直接落实架构文档权衡分析给出的应对方案："当系统提取出的能力树超过一定层级或数量时，交由人类开发者确认后再进行映射计算"——复用文档 04/09 已建立的 `suspend_and_wait` 通用挂起机制，不新造一套审批逻辑。

**实现期的三处修订（以代码为准）**：

1. **挂起前先落一条 `human_approvals` 待办**（`HumanApprovalRepository.create()`，`wait_key = f"{run_id}:coverage:tree_review"`、`thread_id = run_id`），与 `optimizer/loop.py::_suspend()` 同一套写法。不落待办的话审批工作台（文档 22）看不到这张卡片，也就没人能唤醒它。

2. **人工回传的 payload 要被解析，默认不通过**。上面的伪码丢弃了 `suspend_and_wait()` 的返回值，等于"人点了什么都继续"。实现里被认作确认的形状是 `"confirm"` / `{"decision": "confirm"}` / `{"confirmed": true}`，其余（含 `None` 与形状对不上的）一律抛 `PipelineSuspended`。默认不通过是刻意的：一棵没被明确确认过的树若被当成确认过的继续算下去，得到的是一份建立在错误粒度之上、却看起来正常的覆盖率报告；而拒绝的代价只是这个维度停在这里等人——本维度不阻断合并（第 8 节），停下来不会卡住任何人的 CI。

3. **节点返回值只带增量**，不是伪码里的 `{**state, ...}`。`judge_verdict_ids` 的 reducer 是 `operator.add`，回抛整个旧状态会让 id 翻倍（与模块一~五同一条坑）。本节点的返回值是 `{"capability_tree_id": ..., "_coverage_tree_node_count": ...}`（外加人工确认过时的 `_coverage_tree_review_confirmed`）。

⚠️ 挂起恢复后**本节点整体重跑**（LangGraph 动态 `interrupt()` 的语义，全项目一致），即会重新调一次抽取。能力树不会因此错乱（`capability_id` 是确定性哈希、落库是 upsert），代价只是一次 LLM 调用。

## 5. `map_case_coverage`：双向追溯矩阵

```python
async def map_case_coverage(state: PipelineState) -> PipelineState:
    tree = await capability_repository.get(state["capability_tree_id"])
    cases = await test_case_repository.list_by_categories(
        state["active_suite_version_id"], [TestCaseCategory.POSITIVE]
    )   # 只用正向用例做覆盖率映射，与架构文档"遍历所有的正向测试用例"一致
    for case in cases:
        if case.target_capability_ids:   # 已映射过(如上一轮回环中已处理)，跳过重复调用
            continue
        capability_ids = await analyzer_agent.map_case_to_capabilities(case, tree)
        case.target_capability_ids = capability_ids
        await test_case_repository.save(case)
        for cid in capability_ids:
            node = next(n for n in tree.nodes if n.capability_id == cid)
            node.covered = True
            node.covering_case_ids.append(case.case_id)
    await capability_repository.save(tree)
    return state
```

**实现期的五处修订（以代码为准）——第 1 条是一个会让补盲回环永远空转的缺陷**：

1. ⚠️ **"要不要发 LLM 请求"与"要不要标记覆盖"必须分开判断**。上面的 `if case.target_capability_ids: continue` 一次性跳过了两件事，于是**已经带着 `target_capability_ids` 的用例永远不会去标记它们本该覆盖的节点**——而补盲生成的新用例恰恰就是这样：Generator 按 `CapabilityFocus` 的硬性要求，在出题时就回填好了 `target_capability_ids`（见 `docs/dev/interfaces/06` 第 1 节与 `_shared.jinja` 的 `focus_block`）。后果是补盲回环怎么跑覆盖率都不涨，一路空转到迭代上限。实现里的语义是：**已有映射的跳过 LLM 调用，但照常参与覆盖标记。**

2. **每轮进来先把 `covered` / `covering_case_ids` 清空再重算**。伪码直接在读回来的树上 `append`，而这个节点在回环里会被跑第二、第三次，读回来的树已经带着上一轮的结果——同一条用例会被重复 append 进 `covering_case_ids`，而模块七要拿这个列表做用例聚类，重复项会直接扭曲重叠度计算。清空重算是幂等的，代价只是一个内存循环。

3. **`next(n for n in tree.nodes if ...)` 换成字典索引 + 缺失时跳过**。伪码在 id 找不到时会抛 `StopIteration`。这不是假想情况：SKILL.md 改写过某项能力的描述后 id 就变了，旧绑定成为"孤儿"。实现里跳过并打日志（事件名 `coverage_orphan_case_binding`），因为**淘汰与否是模块七"平滑淘汰"的职责**（架构文档要求先向开发者发出确认提示，而不是直接剔除），本文档只负责不让它把流水线掀掉。

4. 映射调用是**并发**的（`asyncio.Semaphore(max_concurrent_mappings)`，默认 10），逐条落库。逐条而不是最后批量存：节点可能崩在中途，已经花掉的调用应当留下结果，下一轮回环靠 `target_capability_ids` 非空就能跳过它们。

5. `active_suite_version_id` 缺失时抛 `PersistenceError` 而不是静默返回：没有用例集时"覆盖率 0%"和"这次没测"是两件完全不同的事。

## 6. `blind_spot_detection`

```python
def blind_spot_detection(state: PipelineState) -> PipelineState:
    tree = ...  # 同步读取
    blind_spots = [n for n in tree.nodes if not n.covered]
    coverage_ratio = 1 - len(blind_spots) / len(tree.nodes) if tree.nodes else 1.0
    verdict = judge_agent.quantitative_verdict(
        subject_id=tree.skill_id, rule_name="capability_coverage_threshold",   # 新增规则注册
        inputs={"coverage_ratio": coverage_ratio, "threshold": settings.coverage.min_coverage_ratio},  # 默认0.9
    )
    return {**state, "_blind_spot_ids": [n.capability_id for n in blind_spots],
            "_coverage_ratio": coverage_ratio, "judge_verdict_ids": [verdict.verdict_id]}
```

```python
def capability_coverage_threshold(inputs: dict) -> JudgeVerdictStatus:
    return JudgeVerdictStatus.PASS if inputs["coverage_ratio"] >= inputs["threshold"] else JudgeVerdictStatus.FAIL
```

（此规则在权重覆盖率——即文档 18——落地后会被**替换**为加权版本，本文档先用未加权的简单比例作为模块六阶段的判定口径，文档 18 明确会覆盖 `capability_coverage_threshold` 规则的实现体，规则名保持不变，调用方——本节点——不需要修改。）

**实现期的五处修订（以代码为准）**：

1. **节点是 `async def` 而不是 `def`**。能力树在 Postgres 里，本项目的仓储层只有异步接口；硬做成同步节点就得在事件循环里阻塞一次数据库读——为了一个纯算术函数的形式好看，换来一次会拖住整张图的阻塞调用，不划算。节点体内的判定逻辑仍然是纯算术，没有 LLM。

2. **`subject_id` 带 `coverage:` 前缀**（约定同 `docs/dev/interfaces/13` 第 6.1 节）。判定对象是整个 Skill 的测试集而不是某一条用例，裸用 `skill_id` 会与将来任何"以 skill 为主体"的判定（文档 17 的瘦身结论、文档 18 的加权覆盖率）在 `JudgeRepository.list_verdicts()` 里混成一堆。

3. **判定显式落一次库**。`quantitative_verdict()` 按 `docs/dev/interfaces/08` 第 1 节的约定不落库，但状态里要带走它的 `verdict_id`——不存的话那个 id 指向一条谁也查不到的记录。本维度每轮只产生一条判定，存一次的代价可以忽略（与模块四/五同样的处理）。

4. **状态里的盲区存"id + 描述"而不是裸 id**（键名 `_coverage_blind_spots`）。两个下游都需要描述：`feedback_driven_generation` 要拿它填 `CapabilityFocus.descriptions`（`docs/dev/interfaces/06` 第 1 节列为必填），报告 findings 里只写一行 `零覆盖能力: skill-x:cap-3f9ac21b0d47` 对读报告的人等于没写——`capability_id` 是描述文本的哈希，不可读也不可猜。

5. `inputs` 里多带一个 `tier_weighted: False` 的**口径标记**（不参与判定）：本阶段所有 `tier` 都是占位值，加权算出来的数与未加权完全一样，但那个"一样"是巧合而不是结论。文档 18 接入时把它翻成 True，历史判定记录据此仍能区分是拿哪种口径算的。

## 7. `feedback_driven_generation`：反向驱动 Generator

```python
async def feedback_driven_generation(state: PipelineState) -> PipelineState:
    iteration = state.get("_coverage_patch_iterations", 0)
    if iteration >= settings.coverage.max_patch_iterations:   # 默认3，防止架构文档提到的"无限重试死锁"
        return {**state, "_coverage_patch_exhausted": True}   # 不再继续回环，直接进入finalize，报告中标注未达标

    skill = await skill_repository.get(state["skill_id"], state["skill_version_ref"])
    focus = CapabilityFocus(capability_ids=state["_blind_spot_ids"])   # 文档06已定义此模型
    new_suite = await generator_service.incremental_patch(
        skill, focus=focus, triggered_by="coverage_gap",
    )
    return {**state, "active_suite_version_id": new_suite.suite_version_id,
            "_coverage_patch_iterations": iteration + 1}
```

`max_patch_iterations` 硬上限直接回应架构文档权衡分析的风险提示："如果 Analyzer Agent 将能力拆解得过于细碎，可能会导致覆盖率永远无法达标，从而引发流水线的无限重试死锁"——本文档不试图从算法上"更聪明地"避免这个问题，而是简单粗暴地设置迭代上限，达到上限仍未达标则报告中如实反映"覆盖率未达阈值"，交给人工判断是能力树切分太细还是测试集真的不足，符合架构文档"应对方案"里"人工审核卡片"的精神——即宁可暴露问题给人，也不让机器在不确定的情况下自我循环空转。

**实现期的三处修订（以代码为准）**：

1. ⚠️ **`CapabilityFocus` 必须带 `descriptions`**。伪码只传了 `capability_ids`。`docs/dev/interfaces/06` 第 1 节把 `descriptions` 列为**必填**并写明了后果："Prompt 里给模型看的是描述，不是裸 id。缺失的 id 会退化为 id 原文，那对模型没有任何信息量，生成出来的用例也就补不到真正的盲区。"而 `capability_id` 恰恰是一串哈希。实现里从 `_coverage_blind_spots` 直接取描述填进去。

2. **`incremental_patch()` 抛 `GenerationError` 时降级而不是抛出**。典型触发条件是"这个 Skill 还没有任何 active 用例集"。本维度不阻断合并，为一次补题失败把整条流水线掀掉不成比例；实现里标记 `_coverage_patch_exhausted` 并把原因写进 `_coverage_patch_failure`，最终出现在报告 findings 里——否则表现为"盲区还在、系统却安静地不补了"。**失败不推进迭代计数**，推进了会让"还剩几次机会"变得不可解释。

3. **迭代上限在两处各拦一次**：节点内部（本节伪码已有）与条件路由 `route_after_blind_spots`。"无限重试死锁"是架构文档给本模块点名的风险，这条上限值得在唯一会推高迭代次数的地方再写一遍，而不是完全托付给图的连线；路由上那一次则让"这个环会不会一直转下去"在图结构里就能回答。

## 8. 报告聚合

```python
async def finalize_dimension_report(state: PipelineState) -> PipelineState:
    await report_generator.record_dimension_result(
        run_id=state["run_id"],
        result=DimensionResult(
            dimension="capability_coverage", status=JudgeVerdictStatus.PASS if state["_coverage_ratio"] >= settings.coverage.min_coverage_ratio else JudgeVerdictStatus.FAIL,
            score=state["_coverage_ratio"],
            findings=[f"零覆盖能力: {cid}" for cid in state["_blind_spot_ids"]],
            blocking=False,   # 见下方说明
        ),
    )
    return state
```

**阻断策略**：覆盖率不足本身**不阻断合并**（`blocking=False`）——覆盖率反映的是"测试是否测得全"，而不是"Skill 本身是否有质量问题"；一个 Skill 完全可以功能正确但测试集尚不完备。本文档把它作为强可见的报告项（供人工/未来 CI 门禁按需收紧），而不是让"测试基础设施尚未完善"直接拖垮一个功能正常的 Skill 的合并。这一策略在文档 24 落地 CI 门禁时可以按项目成熟度调整，本文档只定默认值。

**实现期的三处修订（以代码为准）**：

1. **调用形状是关键字参数而不是 `result=DimensionResult(...)`**。`ReportGenerator.record_dimension_result()` 的签名是 `(*, run_id, dimension, status, score, findings, blocking)`（文档 05 落地时定的），本节伪码那种包一层模型的写法调不通。

2. **状态里取不到数时判 `NEEDS_HUMAN_REVIEW`，不判 PASS/FAIL**。伪码里 `state["_coverage_ratio"]` 缺键会直接 `KeyError`。实现里区分两种"算不出来"：
   - 覆盖率键取不到（主图状态 schema 漏并了本维度私有键，或节点被跳过）；
   - 能力树为空——此时第 6 节的公式给出 `coverage_ratio = 1.0`，但那不是"测得全"而是"根本没抽出能力"，报 PASS 会让一份根本没做覆盖分析的运行看起来满分。
   
   两种情形都判 `NEEDS_HUMAN_REVIEW` 并在 findings 里点名原因。维度级状态的优先级因此是 **NEEDS_HUMAN_REVIEW > FAIL > PASS**，与模块二（FAIL 优先）相反——这里的"待人确认"表示的是"这个数字根本没算出来"，在一个算不出来的数字上判 FAIL 等于用一个假结论替掉"我不知道"。

3. **findings 带描述、带上下文，而不只是裸 id**。除了"零覆盖能力 `<id>`：`<描述>`"，还会写入覆盖率与分母（"N/M 项声明能力被正向用例覆盖，参与映射的正向用例 K 条"）、补盲耗尽的提示、补盲失败的原因、以及能力树是否经过人工确认。这些都是读报告的人判断"该拿这个数字做什么"所必需的。
