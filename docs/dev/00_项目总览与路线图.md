## 1. 项目一句话定义

一个基于 **LangGraph** 构建的、以 **DAG/状态机** 形式编排的 **Skill 评测 CI/CD 流水线**：输入是一份 `SKILL.md`（及其 `scripts/`、`references/`），输出是一份可阻断合并请求的量化评测报告（触发准确度、上下文效率、指令控制力、脚本易用性、安全性、覆盖率、跨模型泛化性、多技能并发鲁棒性），并在必要时自动生成修复补丁或挂起等待人工审批。

## 2. 架构原文 → 工程模块的重新映射

`_5_关键架构.md` 按**评测维度**组织（模块一～模块十一），这是"用户视角/报告视角"的顺序。但工程实现必须按**依赖关系**排序：很多维度共享同一套底层能力（State Schema、Checkpointer、Trace 数据结构、Mini Agent 框架、Judge Agent、Optimizer Agent、Validator Agent、Hermes 适配层……），如果照搬原文顺序开发，会导致模块一里就要重复发明模块十一才有的"裁判可信度"机制、模块三才定义的 Trace Tree 结构。

因此本路线图把开发拆成 **四层**：

```
第 0 层  工程地基（脚手架/Schema/持久化/执行引擎适配/可观测性骨架）
   ↓
第 1 层  跨维度复用的公共智能体（Generator / Executor / Judge / Optimizer / Validator / Mini-Agent 框架）
   ↓
第 2 层  各评测维度的业务节点（对应原文模块一～模块十）
   ↓
第 3 层  系统自证与运维闭环（模块十一元评估、容错与人工审批、数据飞轮、CI/CD 落地）
```

同一层内部的文档，按"越基础越先做"的顺序编号；跨层不回头修改已确认文档的对外接口——只能在预留的"待接入"章节里追加。

## 3. 你提出的两条关键约束，如何落到工程设计里

1. **Generator 节点只在初始化时生成一次，之后只能"手动强制生成"，流水线重复执行默认复用已有测试集。**
   → 落到文档 `04_Generator Agent与测试集生命周期管理` 中，设计为一个显式的 **`generation_mode: {"reuse", "force_regenerate", "incremental_patch"}`** 三态开关，并配合一张 `test_suite_version` 表做版本化存储（复用 pgvector 所在的 Postgres 实例）。模块六/七的"反向驱动补盲区"、模块十一子节点二的"防坍塌"，都通过 `incremental_patch` 模式接入同一个 Generator，而不是各自造轮子。

2. **简单维度用内置 Mini Agent，需要完整执行 Skill 的维度用外置可插拔 Agent（如 Hermes），通过 hook 机制回传执行信息。**
   → 落到文档 `03_执行引擎适配层与Hermes Hook协议` 中，设计一个 **`ExecutorBackend` 抽象接口**（`MiniAgentBackend` 与 `PluggableAgentBackend` 两个实现），以及一份**统一的 Trace Tree JSON Schema**（原文模块三第2节列的 timing/action trajectory/env feedback/artifacts 四大类字段）。所有维度评测节点只面向这个抽象接口编程，不感知底层到底是 Mini Agent 还是 Hermes。

## 4. 全局技术栈基线（后续文档默认遵循，不再重复声明）

| 关注点 | 选型 | 来源 |
|---|---|---|
| 编排引擎 | LangGraph（Python） | 用户指定 |
| 状态持久化 / Checkpoint | `PostgresSaver` | 架构文档"状态持久化与可观测性" |
| 向量检索 | PostgreSQL + `pgvector`，与 Checkpointer 共用实例 | 架构文档"长时记忆与数据飞轮" |
| 混合检索重排 | Dense + BM25 + Cross-Encoder Reranker（HF 轻量模型） | 同上 |
| 外置执行引擎 | 可插拔，默认对接 Hermes-agent（[NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent)），通过 hook 协议接入 | 用户指定 |
| 内置轻量评审 | Mini Agent（低温 0.1，同一 LLM API，仅省去外置沙箱） | 架构文档模块二 |
| 报告双写 | `benchmark.json` + HTML（CI 制品）／Langfuse（可观测性） | 架构文档"状态持久化与可观测性" |
| 人工审批 | `interrupt_before` + Webhook → Discord 卡片 + Base44 审查工作台 | 架构文档"容错机制" |
| CI 宿主 | GitHub Actions（文档中同时提到 GitLab/Jenkins，默认以 GitHub Actions 为参考实现，接口不绑定具体 CI） | 架构文档多处 |
| 安全隔离 | 每次评测使用 Ephemeral Docker 容器，无出站网络或白名单出站 | 架构文档模块五 |
| 语言 | Python ≥ 3.13（沿用现有 `pyproject.toml`） | 现有项目 |

## 7.「待接入文档」机制说明（贯穿全部后续文档）

- 每份开发文档结尾若存在尚未开发的下游依赖，会给出一节 **「待接入文档」**：列出预留的接口签名（函数签名/Pydantic 模型/LangGraph 节点输入输出 State 字段）、当前的桩实现（stub）行为、以及后续模块接入时需要替换的具体位置（文件路径 + 函数名）。
- 每份开发文档开头若依赖前序模块，会先检查前序文档是否已提供「待接入文档」；若前序文档确实预留了对应章节，则按其接口对接；若未预留（说明前序设计有遗漏），本文档会先给前序文档**补一份接入说明**（以独立小节形式标出"补充接入文档"），再继续本模块设计，以保证接口链条不断裂。
- 所有接入文档最终会在 `docs/dev/interfaces/` 目录下沉淀为独立的接口清单文件（每个可复用组件一份），供实际编码阶段直接引用。

## 8. 术语表（后续文档统一使用，不再逐份重复定义）

| 术语 | 定义 |
|---|---|
| Generator Agent | 负责生成正向/反向测试用例的智能体 |
| Executor Agent | 负责实际发起 Skill 触发测试的智能体（走 `ExecutorBackend` 抽象） |
| Judge Agent | 负责对执行结果/Trace 做量化判定的裁判智能体 |
| Optimizer Agent | 负责针对失败用例重写 `SKILL.md`/补丁代码的智能体 |
| Validator Agent | 负责生成/检索确定性校验脚本的智能体 |
| Analyzer Agent | 负责解析 `SKILL.md` 声明能力、拆解原子能力树的智能体（模块六/七/八专用） |
| Attacker Agent | 负责生成红队对抗测试集的智能体（模块五专用） |
| Mini Agent | 内置轻量评审 Agent，仅做文本级/静态分析，不需要外置沙箱 |
| Pluggable Agent | 外置可插拔完整执行 Agent，默认实现为 Hermes-agent |
| Trace Tree | 统一的执行轨迹 JSON 结构（timing / action trajectory / env feedback / artifacts 四段） |
| PipelineState | LangGraph 图的全局共享状态（TypedDict），本项目所有节点的唯一状态契约 |
