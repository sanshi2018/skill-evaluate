### 2.1 贯穿全部实验的"通过"口径

三条对照实验比较的是**触发行为是否符合用例类别的预期**：POSITIVE 期望加载 SKILL.md，NEGATIVE 期望不加载（与模块一两条触发率规则同向）。验证集里两类用例都有，直接拿 `loaded_skill_md` 当"通过"会把"备用代理正确地没有误触发"读成失败。

执行后端对超时/沙箱故障返回的保守失败态 Trace（`loaded_skill_md=False`）**不是证据**：任一臂没有有效执行证据的用例记为"证据不足"，交人工确认。口径集中在 `executors/comparison.py`，模块九节点与共识门控共用。

## 3. `prepare_cross_model_sample`：抽样与异构后端注册

### 3.1 `LlamaControlBackend`

```python
# src/skill_evaluate/executors/llama_backend.py（对文档03待接入项的正式实现）
@register_backend("llama_control")
class LlamaControlBackend(ExecutorBackend):
    backend_type = ExecutorBackendType.PLUGGABLE

    def __init__(self, client: LlamaControlClient | None = None, *, wait_mode: str | None = None, ...): ...
    async def execute(self, request: ExecutionRequest) -> ExecutionTrace: ...   # poll 或 callback
    async def health_check(self) -> bool: ...                                   # client.is_reachable()
```

- **网络交互**抽象为 `LlamaControlClient` 协议（`submit_task` / `get_task` / `is_reachable`）。配置了 `SKILLEVAL_EXECUTOR_LLAMA_CONTROL_ENDPOINT` 时使用 `HttpLlamaControlClient`（按一份最小 REST 契约调用 Llama Agent 运行时），否则注入 `UnconfiguredLlamaControlClient`（提交即抛 `ExecutorBackendError`、健康检查恒 False，**不伪造成功**）。
- **回传协议与 Hermes 同构**：结果体 `LlamaRunPayload` 即 `HermesHookPayload`，经同一个 `map_hermes_payload_to_trace()` 映射——对照实验的两条臂必须用同一套口径生成 Trace；`loaded_skill_md` 缺显式信号时走文档 03 预留的 `read_file` fallback。
- **等待机制（类比文档 03 第 4.4 节）**：
  - `poll`（默认）：提交后进程内按间隔轮询，超过 `wall_clock_timeout_s + 15s` 记 `sandbox_timeout` 失败态。适合 HF Inference Endpoint 这类只提供查询接口的托管方案，不依赖图上下文。
  - `callback`：与 Hermes 完全同构——`pending_hooks` 落库 → `suspend_and_wait()` 挂起 → 运行时回调 `POST /hooks/llama_control/{run_id}/{case_id}/{run_index}`（`api/hooks_llama.py`，`X-Llama-Signature` HMAC 验签，密钥独立于 Hermes）→ `resolve_suspension()` 唤醒。复用文档 04 的通用挂起框架。

REST 契约与运行时侧的硬要求见接入文档第 3 节。

### 3.2 抽样

```python
async def prepare_cross_model_sample(self, state: CrossModelState) -> dict[str, object]:
    suite_version_id = state.get("active_suite_version_id") or (await test_suite_repository.get_active_version(skill_id)).suite_version_id
    cases = await test_case_repository.list_by_categories(suite_version_id, [POSITIVE, NEGATIVE])
    sampled = sample_validation_cases(cases, skill_id=skill_id, ratio=settings.cross_model.sample_ratio)  # 默认0.2
    return {"_xmodel_sample_case_ids": [c.case_id for c in sampled], "_xmodel_sample_note": note}

def sample_validation_cases(cases, *, skill_id, ratio):
    pool = sorted((c for c in cases if c.split is VALIDATION and c.category in (POSITIVE, NEGATIVE)), key=lambda c: c.case_id)
    size = min(len(pool), max(1, round(len(pool) * ratio))) if pool else 0
    return random.Random(f"skill-evaluate:cross-model-sample:{skill_id}").sample(pool, size)
```

- 先按 `case_id` 排序再抽样，且用**字符串种子**（跨进程稳定）——`hash(skill_id)` 受 `PYTHONHASHSEED` 随机化影响，断点恢复后会抽到另一批。与文档 06 第 6 节的确定性 shuffle 同一写法，但种子前缀不同（避免"抽样"与"60/40 划分"两次随机过程相关）。
- 不调用 `ensure_test_suite()`；验证集为空时**不**定向补题（非阻断维度不应拥有改变用例集的权力），空抽样写入 `_xmodel_sample_note` 如实报告。

## 4. `heterogeneous_execution_matrix`：主备代理对比

```python
async def heterogeneous_execution_matrix(self, state):
    if not cases: return skipped
    secondary = deps.secondary()                       # get_backend(settings.cross_model.secondary_backend)
    if not await secondary.health_check(): return skipped("备用代理不可用")
    reference, variant = await self._run_pair(run_id, cases,
        reference=(deps.primary(), skill, RUN_INDEX_XMODEL_PRIMARY, None),     # 路由表 PLUGGABLE → 默认 Hermes
        variant=(secondary, skill, RUN_INDEX_XMODEL_SECONDARY, None))
    outcome = await self._compare(..., rule_name="cross_model_heterogeneous_consistency", subject_prefix="xmodel_hetero:",
        finding=lambda cid: f"[代理差异] {cid} 在主代理上表现符合预期，但在备用代理上不符合，可能存在代理特定的触发依赖")
    return {"executed_trace_ids": [...], "judge_verdict_ids": [...], "_xmodel_hetero_outcome": outcome.model_dump()}
```

- 主代理走路由表（`get_backend_for_node("cross_model_generalization")`），备用代理按配置名取；装配期校验两者不是同一个后端。
- 两条臂**并发**执行、共用一个沙箱信号量（三条并行支路共用同一个），Trace 各落自己的 run_index 号段。
- 判定经量化规则（`JudgeAgent.quantitative_verdict()`），只归档 FAIL 判定。
- 备用代理不可用时跳过本支路并记 `NEEDS_HUMAN_REVIEW`，不让一个非阻断维度的外部依赖拖垮整条流水线。

**这不是评测本身的补丁裁决**，而是**证据收集**——真正的"接受/拒绝补丁"裁决发生在第 7 节的共识门控中。

## 6. `stochastic_ablation_testing`：消融测试与咒语剥离

```python
# src/skill_evaluate/agents/analyzer/ablation_lexicon.py
def ablate(body_markdown: str, seed: int | str, *, drop_probability: float = 0.8) -> AblationResult: ...
def ablate_skill_text(body_markdown: str, seed: int | str, *, drop_probability: float = 0.8) -> str: ...
def ablation_seed(skill_id: str) -> str:  # "skill-evaluate:ablation:{skill_id}"

async def stochastic_ablation_testing(self, state):
    result = ablate(skill.body_markdown, ablation_seed(skill.skill_id), drop_probability=settings.ablation_drop_probability)
    if not result.changed: return not_applicable      # 没有可剥离的措辞：不起沙箱
    ablated_skill = skill.model_copy(update={"body_markdown": result.ablated, "version_ref": f"{skill.version_ref}+ablation", ...})
    reference=(primary, skill, RUN_INDEX_XMODEL_ABLATION_ORIGINAL, None)
    variant=(primary, ablated_skill, RUN_INDEX_XMODEL_ABLATION_ABLATED, None)
    rule_name="cross_model_ablation_robustness", subject_prefix="xmodel_ablation:"
    finding: "[咒语依赖] {case_id} 删除情绪化措辞后即表现不符合预期，Skill 可能过度依赖模型注意力机制而非真实专有知识"
```

词典（正则，允许持续补充、不需要新文档）分六类：思维咒语（"仔细思考""think step by step"）、身份抬举（"你是世界级专家"）、点名模型（"like a Hermes model"）、情绪施压（"务必""一定要""这对我的职业生涯很重要"、许诺奖惩）、全大写强调（`ALWAYS`/`NEVER`）、连串感叹号。消融处理：前四类整段删除；全大写强调**降级为小写**（`NEVER delete` 里的 never 是信息，删掉会把禁令反转成许可）；连串感叹号折叠为一个句号。**围栏代码块与行内代码受保护**（代码是 Skill 的真实专有知识）。随机性只决定哪些命中被删（确定性种子，同一运行可复现）。

**架构文档的核心论点**在此落地为具体可执行的对比实验：如果剥离"咒语"后任务表现变差，说明 Skill 的有效性建立在"讨好特定模型的话术"上而非"真实的领域专有步骤"。

## 7. Pareto 最优补丁裁决：对文档 09 `OptimizationLoop` 的可选门控扩展

架构文档要求"当 Optimizer Agent 针对失败用例提出了 SKILL.md 的修改补丁后，Judge Agent 必须审核该补丁在异构矩阵中的表现"。本文档不回头修改文档 11/15，而是提供**可组合的装饰器**，供各闭环按需叠加：

```python
# src/skill_evaluate/agents/optimizer/consensus_gate.py
def with_quirk_stripping_gate(base_retest_fn: RetestFn, *, baseline_skill: SkillDefinition) -> RetestFn:
    """补丁新写入了咒语式措辞（同一份词典）→ 不跑回归直接打回，detail 前缀 "模型怪癖剥离(Model-Quirk Stripping)"。
    只看新增命中；新增的全大写强调只告警不打回。"""

def with_consensus_gate(
    base_retest_fn: RetestFn, sample_cases: Sequence[TestCase], *, run_id: str,
    baseline_skill: SkillDefinition | None = None, tolerance: float | None = None,   # 默认 0.05
    secondary_backend: ExecutorBackend | None = None, judge=None, runs_per_case=None,
    timeout_s=None, trace_repository=None, max_concurrent=None,
) -> RetestFn:
    """先跑 base_retest_fn（主代理路径原有校验不变），通过后再在备用代理上跑 sample_cases：
    - sample_cases 必须全部来自训练集（门控结果决定补丁取舍，本身就是优化信号），否则构造期 ValueError；
    - 传了 baseline_skill：先在备用代理上测一次原版（缓存），基线通过率 − 候选通过率 > tolerance 即打回；
    - 未传：候选通过率 < 1 − tolerance 即打回；
    - 候选无任何有效证据：打回（fail closed）；
    判定经规则 cross_model_consensus_gate（JudgeAgent.quantitative_verdict），打回时
    LoopResult(passed=False, detail="代理过拟合(Agent Overfitting)：...")。"""
```

推荐叠加顺序：`with_consensus_gate(with_quirk_stripping_gate(retest_fn, baseline_skill=skill), train_sample, run_id=..., baseline_skill=skill)`——静态拦截器零成本先短路，共识门控最贵最后跑。调用方用 `is_agent_overfitting(result)` / `is_model_quirk_rejection(result)` 识别打回原因，不要自己匹配字符串。

**"退化"按相对基线计算**是对架构文档"备用代理的降幅控制在 5% 以内"的直接落实：一份原版只在备用代理上跑通 60% 的 Skill，按绝对口径任何补丁都过不了门，Optimizer 会永远碰壁。

**这是本文档留给文档 11/15 的"可选增强钩子"，不是强制修订。**

## 9. 报告聚合

```python
async def finalize_dimension_report(self, state):
    # FAIL：任一对照实验发现脆弱性，或语言坏味道审查 FAIL
    # NEEDS_HUMAN_REVIEW：抽样为空 / 支路被跳过 / 有用例证据不足 / 审查被黄金盲测占用 / 结果键缺失
    # PASS：其余（消融 not_applicable 属于正常结论）
    await reporter.record_dimension_result(
        run_id=run_id, dimension="cross_model_generalization", status=status,
        score=None, findings=findings, blocking=BLOCKING,   # BLOCKING = False
    )
    return {}
```

`record_dimension_result()` 的实际签名是关键字参数（与文档 11 接入文档第 5 节一致）。

**不阻断的理由**：架构文档权衡分析明确指出该机制"成本与迭代阻力激增"，且建议"权重容忍度"而非绝对红线。本文档采用"高可见度告警 + 不阻断"的策略，把决策权交给人工，与架构文档"在绝对的泛化与商业迭代速度之间取得平衡"的建议一致。若团队后续认为该维度应该阻断，修改 `nodes/cross_model/nodes.py::BLOCKING` 即可（刻意不做成配置项），不需要新文档。

## 11. 实现期对本文原稿的修正记录

| # | 原稿写法 | 实现 | 原因 |
|---|---|---|---|
| 1 | 裸 `loaded_skill_md` 作为"通过" | 触发行为是否符合用例类别预期；失败态 Trace 不计入 | NEGATIVE 用例方向相反；超时 Trace 会凭空制造差异 |
| 2 | 节点内 if/else 追加 findings | 注册三条量化规则 + 门控规则，经 Judge | 文档 08 接入文档第 0 节铁律 |
| 3 | `random.Random(seed=hash(skill_id))` | 排序后字符串种子 | `hash()` 跨进程不稳定、仓储回读顺序不确定 |
| 4 | `test_case_repository.list_by_split(...)` | `list_by_categories()` + 按 split 过滤 | 仓储无该方法，按类别查询是既有接口 |
| 5 | `_cross_model_sample` / `_hetero_findings` 等无前缀键、存对象 | `_xmodel_*` 前缀、只存 case_id、各支路各写结果键 | 文档 11 第 3 节命名空间约定；并行写同一"后写胜"键会互相覆盖 |
| 6 | 节点返回 `{**state, ...}` | 只返回增量 | add reducer 字段会翻倍 |
| 7 | 全部分支 `run_index=0` | 每条臂独立号段（150~220，宽 10） | `(case_id, run_index)` 唯一，会互相覆盖并覆盖模块一的 Trace |
| 8 | 主代理 `get_backend("hermes")` | 路由表 `get_backend_for_node()` | 文档 03 第 5 节：节点不得自行决定后端 |
| 9 | 门控 `secondary_rate < 1 - tolerance` | 默认按相对基线降幅；不传基线才用绝对口径 | 架构文档"降幅控制在 5% 以内" |
| 10 | 门控 `sample_cases` 未限定 split | 必须全部为训练集 | 门控结果是优化信号，验证集不参与优化 |
| 11 | `LoopResult(reasoning=...)` | `LoopResult(detail=...)` + 固定前缀 + 识别函数 | `LoopResult` 只有 `detail` 字段 |
| 12 | 仅有动态门控 | 追加静态 `with_quirk_stripping_gate` | 架构文档"模型怪癖剥离（静态检查拦截器）"；文档 09 接入文档第 3 节提示 |
| 13 | 未处理备用代理不可用 | 健康检查失败则跳过异构矩阵，记 NEEDS_HUMAN_REVIEW | 非阻断维度的外部依赖不应拖垮整条流水线，也不能静默 PASS |
| 14 | 验证集不足时可能定向补题 | 不启用 `cross_model_sampling` | 非阻断维度不应改变用例集 |
