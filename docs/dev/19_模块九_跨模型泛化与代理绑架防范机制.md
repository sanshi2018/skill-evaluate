## 4. `heterogeneous_execution_matrix`：主备代理对比

```python
async def heterogeneous_execution_matrix(state: PipelineState) -> PipelineState:
    skill = await skill_repository.get(state["skill_id"], state["skill_version_ref"])
    primary = get_backend("hermes")
    secondary = get_backend("llama_control")
    findings = []
    for case in state["_cross_model_sample"]:
        primary_trace, secondary_trace = await asyncio.gather(
            primary.execute(ExecutionRequest(skill=skill, case=case, run_index=0)),
            secondary.execute(ExecutionRequest(skill=skill, case=case, run_index=0)),
        )
        await trace_repository.save(primary_trace); await trace_repository.save(secondary_trace)
        if primary_trace.loaded_skill_md and not secondary_trace.loaded_skill_md:
            findings.append(f"[代理差异] {case.case_id} 在主代理触发但备用代理未触发，可能存在代理特定的触发依赖")
    return {**state, "_hetero_findings": findings, "judge_verdict_ids": []}
```

**这不是评测本身的 Pass/Fail 判定**，而是**证据收集**——真正的"接受/拒绝补丁"裁决发生在第 7 节的共识门控中，本节点只负责跑出主备两组 Trace 并做初步差异标记，供报告展示和后续门控判定共同复用（避免重复执行同一批用例）。

## 5. `parameter_perturbation_robustness_probe`：参数扰动鲁棒性

```python
async def parameter_perturbation_robustness_probe(state: PipelineState) -> PipelineState:
    skill = await skill_repository.get(state["skill_id"], state["skill_version_ref"])
    findings = []
    for case in state["_cross_model_sample"]:
        baseline, perturbed = await asyncio.gather(
            get_backend("hermes").execute(ExecutionRequest(skill=skill, case=case, run_index=0, sampling_overrides={"temperature": 0.0})),
            get_backend("hermes").execute(ExecutionRequest(skill=skill, case=case, run_index=0, sampling_overrides={"temperature": 0.2, "top_p": 0.9})),
        )
        if baseline.loaded_skill_md and not perturbed.loaded_skill_md:
            findings.append(f"[脆弱] {case.case_id} 在temperature=0时通过但temperature=0.2时失败，指令逻辑可能过拟合贪心解码路径")
    return {**state, "_perturbation_findings": findings}
```

`sampling_overrides` 字段文档 03 已在 `ExecutionRequest` 中预留（"模块九：temperature/top_p 扰动"），本节点是该字段的首个真实使用方。

## 6. `stochastic_ablation_testing`：消融测试与咒语剥离

```python
def ablate_skill_text(body_markdown: str, seed: int) -> str:
    """随机屏蔽/删减部分形容词、情绪化短语、过度强调标点（正则+词典匹配，
    如"仔细思考""你是一个专家""务必""一定要"等常见AI提示词黑话，词典维护在
    agents/analyzer/ablation_lexicon.py，允许后续持续补充，不需要新文档）。
    确定性随机（同seed同结果），保证同一次评测运行的消融版本可复现。"""

async def stochastic_ablation_testing(state: PipelineState) -> PipelineState:
    skill = await skill_repository.get(state["skill_id"], state["skill_version_ref"])
    ablated_body = ablate_skill_text(skill.body_markdown, seed=hash(state["skill_id"]))
    ablated_skill = skill.model_copy(update={"body_markdown": ablated_body})
    findings = []
    for case in state["_cross_model_sample"]:
        original, ablated = await asyncio.gather(
            get_backend("hermes").execute(ExecutionRequest(skill=skill, case=case, run_index=0)),
            get_backend("hermes").execute(ExecutionRequest(skill=ablated_skill, case=case, run_index=0)),
        )
        if original.loaded_skill_md and not ablated.loaded_skill_md:
            findings.append(f"[咒语依赖] {case.case_id} 删除情绪化措辞后即失败，Skill可能过度依赖模型注意力机制而非真实专有知识")
    return {**state, "_ablation_findings": findings}
```

**架构文档的核心论点**在此落地为具体可执行的对比实验：如果剥离"咒语"后任务失败率显著上升，说明 Skill 的有效性建立在"讨好特定模型的话术"上而非"真实的领域专有步骤"，这正是模块九要防范的"代理绑架"的另一种表现形式（不是绑架在 Hermes 本身，而是绑架在"当前这一代模型对某类措辞的敏感反应"上）。

## 7. Pareto 最优补丁裁决：对文档 09 `OptimizationLoop` 的可选门控扩展

架构文档要求"当 Optimizer Agent 针对失败用例提出了 SKILL.md 的修改补丁后，Judge Agent 必须审核该补丁在异构矩阵中的表现"——这一约束理论上适用于**任何**产出补丁的模块（主要是文档 11 的 description 优化闭环），但文档 11/15 已经确认并各自定义了 `retest_fn`。本文档不回头修改那两份文档，而是提供一个**可组合的装饰器**，供后续实现阶段按需叠加：

```python
# src/skill_evaluate/agents/optimizer/consensus_gate.py
def with_consensus_gate(base_retest_fn: RetestFn, sample_cases: list[TestCase], tolerance: float = 0.05) -> RetestFn:
    """包装任意已有的retest_fn：先跑base_retest_fn(主代理路径的原有校验逻辑不变)，
    通过后额外用llama_control对sample_cases重跑一遍，
    若备用代理的通过率相对基线下降超过tolerance，则整体判定LoopResult(passed=False)，
    reasoning标注为"代理过拟合(Agent Overfitting)"而非普通的功能回归失败——
    这个区分很重要：调用方(如未来接入的appsec_optimizer_loop)可以按reasoning内容
    决定是否需要针对性地要求Optimizer换一种更通用的表达方式重新生成补丁。"""

    async def gated_retest_fn(working_skill: SkillDefinition) -> LoopResult:
        base_result = await base_retest_fn(working_skill)
        if not base_result.passed:
            return base_result
        secondary = get_backend("llama_control")
        secondary_pass_count = 0
        for case in sample_cases:
            trace = await secondary.execute(ExecutionRequest(skill=working_skill, case=case, run_index=0))
            if trace.loaded_skill_md:
                secondary_pass_count += 1
        secondary_rate = secondary_pass_count / len(sample_cases) if sample_cases else 1.0
        if secondary_rate < (1 - tolerance):
            return LoopResult(passed=False, detail=f"代理过拟合(Agent Overfitting)：备用代理通过率仅{secondary_rate:.0%}")
        return base_result
    return gated_retest_fn
```

**这是本文档留给文档 11/15 的一个"可选增强钩子"，不是强制修订**——文档 11/15 在实现阶段可以选择用 `with_consensus_gate(retest_fn, sample_cases=...)` 包一层来获得代理过拟合防护，也可以维持原样先上线。这个设计选择遵循"不回头修改已确认文档接口"的项目约定，同时把架构文档要求的能力以最小侵入的方式提供出来。

```python
async def finalize_dimension_report(state: PipelineState) -> PipelineState:
    all_findings = state["_hetero_findings"] + state["_perturbation_findings"] + state["_ablation_findings"]
    await report_generator.record_dimension_result(
        run_id=state["run_id"],
        result=DimensionResult(
            dimension="cross_model_generalization",
            status=JudgeVerdictStatus.FAIL if all_findings else JudgeVerdictStatus.PASS,
            score=None, findings=all_findings,
            blocking=False,   # 泛化性问题是重要信号但不直接阻断合并——理由见下方
        ),
    )
    return state
```

**不阻断的理由**：架构文档权衡分析明确指出该机制"成本与迭代阻力激增"，且建议"权重容忍度"而非绝对红线。本文档采用"高可见度告警 + 不阻断"的策略，把决策权交给人工（是否接受一个"目前只在 Hermes 上稳定但尚未验证泛化性"的 Skill 先上线），与架构文档"在绝对的泛化与商业迭代速度之间取得平衡"的建议一致。若团队后续认为该维度应该阻断，属于运维层面的策略调整（修改 `blocking` 取值），不需要新文档。
