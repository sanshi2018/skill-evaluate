## 1. 本文档目标

架构文档模块十内容庞大（触发劫持、指令拮抗、上下文挤兑、命名空间污染、增量回归、四项"深度补充"），本文档按"评测系统实际要做什么动作"归并为八个节点，覆盖原文关切点，同时用固定"基准干扰包"控制组合爆炸成本——这是架构文档权衡分析给出的明确应对方案，本文档严格落实（不做全量两两组合测试）。

## 2. 基准干扰包（Benchmark Noise Pack）与配置

```python
# config.py：MultiSkillSettings（挂到 Settings.multi_skill）
class MultiSkillSettings(BaseSettings):
    model_config = SettingsConfigDict(env_prefix="SKILLEVAL_MULTISKILL_")
    noise_pack_skill_ids: list[str] = []          # 3~5 个代表各类冲突类型的固定技能 ID
    core_skill_ids: list[str] = []                 # Top 5 调用频率最高的基石技能 ID（增量回归）
    context_flood_target_tokens: int = 80000       # 上下文挤兑目标水位（证据强度标注用）
    context_flood_near_ratio: float = 0.5          # 达到目标水位的多大比例算"逼近"
    max_hijack_probe_cases: int = 5                # 触发劫持：POSITIVE 用例上限（每条跑单测+并发）
    multi_skill_case_count: int = 6                # MULTI_SKILL 复合用例出题条数（仅一条都没有时出）
    max_antagonism_probe_cases: int = 6            # 指令拮抗：复合用例上限
    max_temporal_probe_cases: int = 3              # 时序扰动：用例上限
    deadlock_min_ping_pong: int = 3                # "A→B→A" 往返几次算高频交替报错
    core_regression_sample_size: int = 5           # 每个核心 Skill 抽几条 POSITIVE 用例
    core_regression_min_rate: float = 0.8          # 核心 Skill 触发率安全下限
    deep_conflict_alert_threshold: int = 3         # 软性冲突发现累计几条触发深度冲突告警
    execution_timeout_s: int = 90                  # 单次并发执行墙钟超时
```

`noise_pack_skill_ids`/`core_skill_ids` 由运维侧维护（本文档只消费不生产），指向已经经 `SkillRepository.save()` 入库的技能；本维度按 skill_id 取**最新入库版本**（`SkillRepository.get_latest()`，本文档新增）。基准干扰包应覆盖典型冲突类型：功能相似易混淆（"Excel处理"对"CSV分析"）、角色设定冲突（"严谨DBA"对"发散导师"）、输出格式冲突（"仅JSON"对"仅Markdown"）。规模不在 3~5 时只写说明、不阻止运行；为空时全部动态探测 `skipped`，维度记 `NEEDS_HUMAN_REVIEW`。

## 5. `namespace_pollution_static_scan`：纯代码命名冲突检测

`probes.find_tool_name_collisions([target, *noise_pack])` 按 `scripts[*].exposed_tool_name`（大小写不敏感）找出被 ≥2 个 Skill 暴露的工具名。**只有涉及被测 Skill 的冲突**经规则 `multi_skill_namespace_collision` 记为发现；干扰包内部彼此撞名写说明行；未带命名空间前缀（`csv-cleaner` → `csv_cleaner_` / `csv_`）的工具名作为建议项。

纯代码检查成本最低，排在最前——若命名已冲突，后续动态探测的很多现象本质上是它的直接后果，报告里可以把"根因"和"症状"关联着看。

## 6. `cross_trigger_interference_probe`：触发劫持探测

```python
cases = POSITIVE 用例（非 COLD，按 case_id 排序）[: max_hijack_probe_cases]
solo, crowded = await gather(execute(cases, run_index=230, background=[]),
                             execute(cases, run_index=231, background=noise_pack))
for case in cases:
    solo_attr = attribute_skill_loads(solo[case], target=target, background=[])
    crowded_attr = attribute_skill_loads(crowded[case], target=target, background=noise_pack)
    # 任一臂是失败态 Trace 或加载归因矛盾 → 证据不足
    judge.quantitative_verdict(rule="multi_skill_trigger_hijack",
                               inputs={"reference_ok": solo_attr.target_loaded, "variant_ok": crowded_attr.target_loaded})
    judge.quantitative_verdict(rule="multi_skill_background_overtrigger",
                               inputs={"background_loaded_count": len(crowded_attr.background_loaded_ids)})
```

- **单测基线必须跑**：只有"单测触发、并发不触发"才算劫持；单测就不触发的是模块一的问题，写说明不计入。
- **加载归因**（`executors/skill_attribution.py`）：沙箱里同时存在多份 SKILL.md 时，`loaded_skill_md` 的路径兜底会被背景技能误导；本维度按挂载目录名（`skills/<skill_id>/SKILL.md`）把读取归到具体 Skill，同时观测"干扰包里哪个技能被意外激活"。

`ExecutionRequest.background_skills` 字段文档 03 已预留，本文档是其首个真实使用方——`HermesSandboxClient.create_sandbox()` 实现需把目标与背景技能分别挂到以 skill_id 命名的独立目录并注入技能列表，且显式上报目标的 `skill_md_loaded`（契约已追加到 `interfaces/03_hermes_sandbox_client.md`）。

## 7. `instruction_antagonism_and_semantic_flow_probe`：指令拮抗与语义流转

```python
traces = await execute(multi_cases[: max_antagonism_probe_cases], run_index=232, background=noise_pack)
for case in cases:
    if not is_conclusive_trace(trace): inconclusive（超时可能正是死锁的表现，交人工）
    ping_pong = probes.count_error_ping_pong(trace.actions)     # 错误动作签名折叠后数 A→B→A 往返
    judge.quantitative_verdict(rule="multi_skill_instruction_deadlock",
                               inputs={"ping_pong_count": ping_pong, "threshold": settings.deadlock_min_ping_pong})
    judge.judgmental_verdict(subject_id=f"multi_skill_flow:{case_id}", template_key="semantic_flow_friction",
                             content={"prompt": ..., "background_skills": ..., "actions": format_actions_for_review(trace)},
                             criticality=Criticality.ROUTINE)
    # 有效执行 + 目标已加载 + 无死锁 → 记入 healthy_case_ids（供时序扰动做参照）
```

死锁判定用确定性规则（错误签名 = `action_type:脚本名`，折叠相邻重复后计数，对同一个校验器连续重试是模块三的"反复试错"，不计入），语义断层判定用 LLM，两者同节点不同判定路径——"量化优先、裁量兜底"。

## 8. `context_exhaustion_attention_decay_probe`：上下文挤兑与注意力衰减

```python
tree = await capability_repository.get(skill_id, version_ref)      # 无树 → skipped；无约束 → not_applicable
constraint, case = 约束按 id 升序，取 covering_case_ids ∪ 用例自带 negative_constraint_ids 中活跃 POSITIVE 用例的最小 case_id
solo, crowded = await gather(execute([case], 233, background=[]), execute([case], 234, background=noise_pack))
for arm in (solo, crowded):
    judge.judgmental_verdict(template_key="negative_constraint_adherence",      # 本文档新增模板
                             content={"constraint_description", "case_prompt", "actions", "final_response"}, ...)
judge.quantitative_verdict(rule="multi_skill_attention_decay", inputs={"reference_ok": solo 遵守, "variant_ok": crowded 遵守})
```

**复用文档 18 的负向约束覆盖映射**挑现成探针用例，单测与并发用同一条用例。原伪代码设想复用"判定用例是否探测约束"的方法判定遵守与否，但那个方法看的是题面、看不到 Trace，因此新增 `negative_constraint_adherence` 模板判"这次执行守没守"。

Token 水位（`crowded_trace.timing.total_tokens` 对比 `context_flood_target_tokens × context_flood_near_ratio`）只做**证据强度标注**：未逼近时报告写明"未发现衰减的结论强度有限"。本系统不向沙箱塞无关填充物去人为撑高上下文——那会引入新的变量。

## 9. `role_collision_and_temporal_static_scan`：角色分裂与时序脆弱性

- **角色冲突**：`role_persona_conflict` 模板，`content={"skill_md": 被测正文, "noise_pack_descriptions": probes.format_noise_pack_for_review(noise_pack)}`——后者含各干扰技能的描述**和从正文抽出的角色/风格预设句**（角色设定通常写在正文而非 description 里）。词典（模块九 `ablation_lexicon`）命中的身份抬举措辞作为"风格强制降级"建议写进说明行。
- **时序扰动**：只从指令拮抗的 `healthy_case_ids` 中取（参照臂在同一环境下健康，打乱后出问题才能归因于顺序）。`probes.shuffle_step_order()` 按句末标点/顺序连接词拆步骤、剥掉"先/然后/最后"等顺序标记后确定性打乱；拆不出 ≥2 步的题面跳过。打乱后崩溃/超时、未触发目标或陷入交替报错 → 规则 `multi_skill_temporal_fragility` 判拓扑脆弱，建议补充显式 Checklist（崩溃场景附注"请人工排除基础设施故障"）。

## 10. `core_skill_regression_gate`：基石技能增量回归熔断

```python
for core in core_skills:
    active = await test_suite_repository.get_active_version(core.skill_id)     # 只读，不为核心 Skill 出题
    cases = POSITIVE（非 COLD，按 case_id）[: core_regression_sample_size]     # 没有 → 证据不足
    baseline = execute(cases, skill=core, run_index=236, background=[])
    crowded  = execute(cases, skill=core, run_index=237, background=[target])
    judge.quantitative_verdict(rule="multi_skill_core_regression",
        inputs={"baseline_loaded", "baseline_conclusive", "crowded_loaded", "crowded_conclusive", "min_rate"})
```

**这一节点是架构文档"熔断拦截"机制的直接实现**：反过来测"引入这个新 Skill 是否伤害了系统里已有的核心 Skill"，因此 `background_skills=[target]`。判定要求**并发触发率 < 安全下限 且 低于该核心 Skill 独立执行的触发率**——只看下限会把核心 Skill 既有的弱点算到本次提交头上，而这是全模块唯一阻断合并的判定。任一臂没有有效证据时记"证据不足"（维度 `NEEDS_HUMAN_REVIEW`），不读成"没有回归"。

## 11. 报告聚合与阻断策略

| 情形 | status | blocking |
|---|---|---|
| 基石熔断 | FAIL | **True** |
| 其余任一冲突发现（劫持、过触发、死锁、语义断层、衰减、角色冲突、拓扑脆弱、命名污染） | FAIL | False |
| 有探测 `skipped` / 证据不足 / 结果键缺失 | NEEDS_HUMAN_REVIEW | False |
| 其余 | PASS | False |

`score=None`。findings 顺序：硬发现 → 软发现 → 说明行（准备阶段说明、统计、参照臂失败、建议项；相同说明合并为一行）。

**阻断策略取舍**：基石回归熔断是唯一默认阻断项，与架构文档"流水线将直接阻断此次合并"对应；其余冲突现象大多需要人工判断"是背景干扰包的问题还是目标 Skill 的问题"，走告警 + 人工审查，延续"确定性硬伤阻断、复杂/主观问题走人工"的分层原则。阻断策略是常量（`BLOCKING_OUTCOME_KEYS`），刻意不做配置项。

## 12. 深度冲突告警：接入文档 22

告警条件：存在基石熔断，**或**软性冲突发现 ≥ `deep_conflict_alert_threshold`。

```python
await dispatch_alert(deps.alerts(), alert_type="deep_multi_skill_conflict", run_id=run_id,
    payload={"dimension", "skill_id", "skill_version_ref", "blocking", "hard_findings", "soft_findings", "noise_pack"})
```

通用告警接口放在 `observability/alerts.py`：`AlertDispatcher` 协议 + 进程级注册点 `set_alert_dispatcher()`，默认 `LoggingAlertDispatcher` 只写结构化日志 `alert_dispatched`。文档 22 实现 Discord 卡片与工作台深度链接后注册真实分发器即可，本维度不改代码。`dispatch_alert()` 吞掉通道异常（告警是旁路）；payload 的 `blocking` 供 22 决定"阻塞挂起"还是"只发通知"。收尾节点把是否发出告警写入 `_multi_skill_alert_dispatched`。

## 14. 实现修订汇总（相对原伪代码）

1. 判定全部经 Judge：原伪代码在节点里 if/else 追加 findings，改为 7 条量化规则 + 3 个裁量模板。
2. 触发劫持增加单测基线臂；新增加载归因（`executors/skill_attribution.py`），同时解决路径兜底误判与背景过触发观测。
3. 失败态 Trace 不作为证据（沿用模块九口径），时序扰动例外并注明。
4. 注意力衰减新增 `negative_constraint_adherence` 模板（原设想复用的模块八方法看不到 Trace）。
5. 基石熔断增加独立执行基线；原 `list_by_categories_for_skill()` 不存在，改为读核心 Skill 自己的 active 用例集。
6. 原 `skill_repository.get_latest()` 不存在，已新增到 `SkillRepository`。
7. `ensure_test_suite()` / `GenerationRequest` 追加 `background_skills`，MULTI_SKILL 模板据此渲染协作对象。
8. 状态只存技能引用、各探测写独立结果键、节点只返回增量（原 `{**state, ...}` 会让 add-reducer 字段翻倍）。
9. `alert_dispatcher` 原为悬空引用，落为 `observability/alerts.py` 的协议 + 注册点。
