## 3. `static_metrics_scan`：硬性扫描

```python
# src/skill_evaluate/nodes/context_scoping/static_scan.py
class StaticMetricsResult(BaseModel):
    line_count: int
    token_count: int
    line_limit_exceeded: bool
    token_limit_exceeded: bool


def scan_static_metrics(skill: SkillDefinition, line_limit: int = 500, token_limit: int = 5000) -> StaticMetricsResult:
    return StaticMetricsResult(
        line_count=skill.line_count,
        token_count=skill.token_count,
        line_limit_exceeded=skill.line_count > line_limit,
        token_limit_exceeded=skill.token_count > token_limit,
    )
```

`skill.line_count` / `skill.token_count` 在文档 02 `SkillDefinition` 中已定义为字段——本文档明确其计算口径：**行数**为 `body_markdown.splitlines()` 长度；**Token 数**使用与 `LLMSettings.provider` 匹配的官方 tokenizer（如 Anthropic 则用其 token 计数工具）离线计算，计算逻辑放在 `skill/loader.py`（文档 01 已规划 `state/skill.py` 存模型，本文档新增 `agents` 无关的纯解析模块 `src/skill_evaluate/ingestion/skill_loader.py`，负责从磁盘路径解析出 `SkillDefinition` 实例——这是本文档对项目脚手架的一次结构性补充，后续所有需要"读取一份 SKILL.md"的文档都复用这个 loader，不重复实现解析逻辑）。

阈值本身（500 行 / 5000 Token）在 `ExecutorSettings` 旁新增 `ContextScopingSettings`（追加式扩展 `config.py`），可配置但默认值取自架构文档明确给出的数字。

## 4. `progressive_disclosure_static_scan`：目录结构审查

```python
def scan_progressive_disclosure(skill: SkillDefinition) -> list[str]:
    """返回缺少'按需加载触发条件说明'的 reference file 路径列表。
    判定规则：对每个 skill.reference_files 中的条目，检查 skill.body_markdown 中
    是否存在指向该文件路径的引用文本，且该引用文本附近（同一段落/同一列表项）
    包含条件性表述（正则匹配"当...""如果...""遇到...时"等触发词 + 文件路径的邻近共现）。
    这是正则启发式，允许一定误报——误报由第5节 Mini Agent 复核兜底，
    而不是把这一步做成精确解析器（架构文档本身也只要求"正则或语法树分析"）。"""
```

命中的"缺失触发条件说明"列表，作为第 5 节 Mini Agent 审查模板 `progressive_disclosure_static` 的输入之一（`content["candidate_missing_triggers"]`），让 LLM 复核这份正则初筛结果里哪些是真问题、哪些是正则误报——两阶段结合，兼顾成本和准确度。

## 5. `mini_agent_peer_review`：三项并发评审

```python
async def mini_agent_peer_review(state: PipelineState) -> PipelineState:
    skill = await skill_repository.get(state["skill_id"], state["skill_version_ref"])
    reviews = await asyncio.gather(
        judge_agent.judgmental_verdict(
            subject_id=skill.skill_id, template_key="omission_audit",
            content={"skill_md": skill.body_markdown}, criticality=Criticality.ROUTINE,
        ),
        judge_agent.judgmental_verdict(
            subject_id=skill.skill_id, template_key="scoping_check",
            content={"skill_md": skill.body_markdown}, criticality=Criticality.ROUTINE,
        ),
        judge_agent.judgmental_verdict(
            subject_id=skill.skill_id, template_key="progressive_disclosure_static",
            content={
                "skill_md": skill.body_markdown,
                "candidate_missing_triggers": state["_missing_trigger_candidates"],
            },
            criticality=Criticality.ROUTINE,
        ),
    )
    return {**state, "judge_verdict_ids": [r.verdict_id for r in reviews], "_peer_review_verdicts": reviews}
```

三项均声明 `Criticality.ROUTINE`——架构文档模块二的权衡分析里明确承认"静态审查可能存在纸上谈兵风险"，本文档的应对方式**不是**把它们升级为 `CRITICAL` 走三倍成本共识投票（那是为"高危/低覆盖率"这类后果严重的判定保留的），而是把这一权衡记录在报告的 `findings` 中并保持较低的整体 `blocking` 强度（见第 6 节），与架构文档"在判定阈值上保留一定宽容度"的建议一致。

## 6. 报告聚合与阻断策略

```python
async def finalize_dimension_report(state: PipelineState) -> PipelineState:
    metrics: StaticMetricsResult = state["_static_metrics"]
    hard_fail = metrics.line_limit_exceeded or metrics.token_limit_exceeded

    peer_findings = [
        f"{v.reasoning[:200]}" for v in state["_peer_review_verdicts"] if v.status == JudgeVerdictStatus.FAIL
    ]

    await report_generator.record_dimension_result(
        run_id=state["run_id"],
        result=DimensionResult(
            dimension="context_scoping",
            status=JudgeVerdictStatus.FAIL if (hard_fail or peer_findings) else JudgeVerdictStatus.PASS,
            score=None,   # 本维度不产出连续分数，只有硬性指标+审查结论
            findings=[
                *( [f"行数 {metrics.line_count}/{500} 或 Token 数 {metrics.token_count}/{5000} 超标"] if hard_fail else [] ),
                *peer_findings,
            ],
            blocking=hard_fail,   # 关键策略：硬性指标超标 -> Hard Fail 阻断；
                                   # Mini Agent 主观审查发现的问题 -> 记录但不阻断（Warning），
                                   # 与架构文档"超标直接抛出 Warning 或 Error"的表述对应：
                                   # 硬性数字用 Error（阻断），主观判断用 Warning（不阻断）。
        ),
    )
    return state
```

**这一区分是本文档对架构文档的关键工程化决策**：架构文档原文对硬性指标说"抛出 Warning 或 Error"（留有余地），本文档明确收窄为"超标即 Error/阻断"——因为 500 行/5000 Token 是可以精确计算、不存在歧义的确定性指标，没有必要对其设置宽容度；而 Mini Agent 的主观判断（常识剥离、范围连贯性）本质上是"建议"，直接阻断合并请求的风险是产生过多误报导致开发者对流水线失去信任，因此定为非阻断的 Warning，只在报告中呈现供人工参考。
