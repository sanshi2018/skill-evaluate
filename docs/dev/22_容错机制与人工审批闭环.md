## 1. 本文档目标

全项目截至目前散落了六处"需要人类介入"的场景（Optimizer 最大重试、Judge 冻结、孤儿用例建议、深度多技能冲突、生成坍塌连续失败、能力树规模确认），本文档提供**统一**的人工审批数据模型、Discord 通知格式、审查工作台 API 契约，把这六处场景收口到同一套机制下，而不是各自为政。

## 2. 统一的人工决策模型

```python
# src/skill_evaluate/state/approval.py
class ApprovalDecisionType(StrEnum):
    ACCEPT_PATCH = "accept_patch"                # 09: 接受Optimizer候选补丁
    ABANDON_RUN = "abandon_run"                    # 09/16/21等: 放弃本次评测，标记最终失败
    UNFREEZE_JUDGE = "unfreeze_judge"                # 08: 解冻Judge Agent配置
    CONFIRM_TREE_REVIEW = "confirm_tree_review"        # 16: 确认能力树规模，继续映射计算
    RESOLVE_DEEP_CONFLICT = "resolve_deep_conflict"      # 20: 记录多技能冲突的人工裁定说明
    INJECT_NEW_SEED = "inject_new_seed"                    # 21: 人工补充种子数据后恢复Generator
    CONFIRM_ORPHAN_RETIREMENT = "confirm_orphan_retirement"  # 17: 非阻塞队列，走独立API而非suspend流程(见第6节)

class PendingApproval(BaseModel):   # ⚠️ 实现追加 node_name / thread_id / blocking / resolved_at，status 为枚举，见第 10 节
    approval_id: str
    run_id: str
    wait_key: str                    # 对应文档04 suspend_and_wait 的 wait_key
    decision_type: ApprovalDecisionType
    context_summary: str               # 人类在Discord卡片/工作台看到的摘要
    context_ref: dict                    # 指向具体证据的引用(如patch_id/finding_ids/case_ids)
    status: str                            # "pending" | "resolved"
    created_at: datetime

class ApprovalDecision(BaseModel):
    approval_id: str
    decided_by: str          # 人类操作者标识(邮箱/用户名，非本项目负责鉴权细节，见第5节)
    outcome: str               # 与decision_type对应的具体选项("approve"/"reject"/"custom_note"等)
    note: str | None = None
    decided_at: datetime
```

新表 `pending_approvals` / `approval_decisions`（文档 04 Alembic 追加，替换其占位的 `human_approvals` 表定义）。

> ⚠️ 实现**未替换** `human_approvals`：它已是 `resolve_suspension()` 的挂起账本，保留为账本层，`pending_approvals` 作业务卡片层（迁移 `0010_approval_workbench`），见第 10 节。

## 3. 统一的挂起触发入口

```python
# src/skill_evaluate/persistence/approval_service.py   ⚠️ 实现为 ApprovalService 类 + 同名模块级函数，追加 node_name/skill_id/thread_id/reason 参数，见第 10 节
async def request_human_approval(
    run_id: str, wait_key: str, decision_type: ApprovalDecisionType,
    context_summary: str, context_ref: dict,
) -> Any:
    """所有需要人工审批的场景统一调用此函数，而不是各自直接调用文档04的suspend_and_wait——
    本函数内部：1) 落一条PendingApproval记录 2) 格式化并发送Discord告警(第4节)
    3) 调用suspend_and_wait()真正挂起图执行。返回值是resume时传入的payload，
    调用方（如09文档的OptimizationLoop）据此决定后续走向。"""
    await pending_approval_repository.save(PendingApproval(...))
    await _send_discord_card(decision_type, context_summary, run_id, wait_key)
    return await suspend_and_wait(reason=decision_type.value, wait_key=wait_key)
```

> ⚠️ 实现补充：非阻塞通知走 `ApprovalService.notify_human()`；Judge 冻结 / 连续坍塌 / 其余 `PipelineSuspended` 不在各自的 Agent 内部挂起，而是由节点级 guard（`nodes/approval_guard.py`）统一接住后调用本函数，见第 10 节。

文档 09 第 5 节的 `suspend_and_wait()` 直接调用点，在实现阶段统一替换为 `request_human_approval()`（对文档 09 实现细节的一处补充说明，不改变 `OptimizationLoop.run()` 的对外签名——`suspend_and_wait` 与 `request_human_approval` 在返回值语义上兼容，只是后者多做了记录+通知两步）。文档 08（Judge 冻结）、文档 16（能力树规模确认）、文档 21（生成坍塌）在各自实现阶段同样改用本函数，本文档不需要回头修改那几份已确认文档的设计文本，只需在实现阶段统一收口调用方式（与文档 19 处理 `with_consensus_gate` 时的"可选钩子"思路一致，此处是"统一收口点"而非可选，因为这是纯粹的实现细节替换，不改变任何已确认的接口行为）。

## 4. Discord Webhook 交互式审批卡片

```python
# src/skill_evaluate/observability/discord_notifier.py
async def _send_discord_card(decision_type: ApprovalDecisionType, summary: str, run_id: str, wait_key: str) -> None:
    payload = {
        "embeds": [{
            "title": f"[待审批] {decision_type.value}",
            "description": summary,
            "fields": [
                {"name": "run_id", "value": run_id},
                {"name": "审查工作台", "value": f"{settings.approval.workbench_base_url}/runs/{run_id}?wait_key={wait_key}"},
            ],
            "color": _color_for(decision_type),
        }],
    }
    await httpx_client.post(settings.approval.discord_webhook_url, json=payload)
```

新增 `ApprovalSettings`（追加式扩展 `config.py`）：`discord_webhook_url`、`workbench_base_url`（⚠️ 实现追加 `hmac_secret` / `notify_timeout_s` / `max_approval_rounds_per_node`；卡片由 `observability/discord_notifier.py::DiscordApprovalNotifier` 发送，同文件的 `DiscordAlertDispatcher` 作为 `interfaces/20` 留下的真实告警通道）。Discord 卡片本身只是**通知**，不是决策渠道——真正的批准/拒绝操作在审查工作台（第 5 节）完成，卡片只提供深度链接跳转，这与架构文档"开发者可以在聊天界面直接查看失败的评测用例和当前 SKILL.md 的差异"的描述略有取舍：本文档选择让 Discord 承担"通知+导流"角色而非"决策"角色，理由是结构化的差异比对、多份 Trace 并排展示这类交互，在聊天软件内实现的体验和可维护性远不如一个专门的 Web 工作台，与架构文档对 Base44 工作台的定位（"全景视图审查""并排比对"）保持一致。

## 5. 审查工作台 API 契约（Base44 或其他前端消费）

与文档 18 对 Base44 热力图的处理方式相同：**本项目不实现工作台前端本身**，只定义并实现它需要消费的后端 API 契约，工作台侧的具体搭建（Base44 或自建 Web 应用）是独立的运维/前端任务。

```
GET  /api/approvals?status=pending          -> list[PendingApproval]
GET  /api/approvals/{approval_id}/context    -> 展开context_ref引用的具体证据
                                                 (如patch_id对应的Patch.diff、trace_id对应的完整ExecutionTrace，
                                                 单测vs并发的双路Trace并排数据等——具体展开逻辑视decision_type分派)
POST /api/approvals/{approval_id}/decide     -> body: ApprovalDecision，触发resolve流程(第6节)
                                                 ⚠️ 实现 body 为 ApprovalDecisionRequest{decided_by,outcome,note}

GET  /api/suggestions?status=pending          -> list[TestCaseSuggestion]（文档17，非阻塞队列，独立于approvals）
POST /api/suggestions/{suggestion_id}/decide   -> 确认/拒绝孤儿用例退役建议
POST /hooks/approval/{run_id}/{node_name}      -> ⚠️ 实现追加：HMAC 签名的机器对机器回调（interfaces/05）
```

**鉴权边界声明**：本文档不设计具体的用户鉴权/权限系统（谁有权限批准生产环境合并），假定这些 API 部署在内部网络或配合团队已有的 SSO/网关方案，具体接入方式属于运维部署范畴，不在本项目代码库的开发文档范围内——这与文档 18 对 Base44 集成、文档 10 对断言工具箱仓库权限的处理原则一致：本项目边界止于"定义清晰、稳定、可被外部系统消费的契约"。

## 6. 决策处理：`POST /api/approvals/{approval_id}/decide`

```python
# src/skill_evaluate/api/hooks_approval.py（对文档05占位文件的正式实现）
# ⚠️ 实现顺序改为：前置校验(含 resumer 已注册) → 副作用(解冻) → 存决定 → mark_resolved → resolve_suspension，见第 10 节
@router.post("/api/approvals/{approval_id}/decide")
async def decide_approval(approval_id: str, decision: ApprovalDecision):
    approval = await pending_approval_repository.get(approval_id)
    await approval_decision_repository.save(decision)

    resume_payload = _build_resume_payload(approval.decision_type, decision)
    await resolve_suspension(
        wait_key=approval.wait_key, resume_payload=resume_payload,
        thread_id=f"{_skill_id_of(approval.run_id)}:{approval.run_id}",
    )
    await pending_approval_repository.mark_resolved(approval_id)
    return {"status": "resolved"}
```

### 8.1 `RESOLVE_DEEP_CONFLICT` 的双模式说明

文档 20 中深度冲突告警本身不一定伴随阻断（只有基石回归熔断阻断）。本文档区分：若触发告警的同时该维度 `blocking=True`（基石熔断场景），走阻塞挂起，流水线真正等待人工处理；若只是告警阈值触发（`blocking=False`），`request_human_approval()` 不会被调用，而是走一条更轻量的路径——只发送 Discord 通知 + 写一条 `PendingApproval(status="pending")` 记录供工作台展示，但**不**调用 `suspend_and_wait()`（流水线继续往下跑，不等待）。这是本文档对"阻塞 vs 非阻塞"人工介入模式的第二次应用（第一次是第 17 文档的孤儿用例），确立为项目级的通用模式：**是否挂起，取决于"不等待人工确认能否继续产出有意义的结果"，而不是"问题是否重要"**——深度冲突即使重要，只要流水线的其余部分不受它阻塞，就不必让它拖慢整体评测。
