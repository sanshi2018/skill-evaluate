## 1. 本文档目标

这是架构文档中最复杂的评测维度，本文档拆成四个相对独立的子节点分别实现，最后统一聚合报告：

1. **A/B 增值对比**：加载 Skill vs. 不加载 Skill 的基线对比，判定 ROI。
2. **Trace 深度审查**：效率诊断（是否反复试错/盲目执行/选择困难）。
3. **控制标定静态扫描**：复用文档 07 模板 5.7，判断刚性/柔性控制是否与任务脆弱性匹配。
4. **渐进式披露动态探查**：区分静态版（文档 12，纯文本审查触发条件是否写清楚）与本文档的**动态版**（真实执行观察 Agent 是否按条件读取参考文件）。

## 4. `ab_comparative_execution`：A/B 对比

```python
async def ab_comparative_execution(state: PipelineState) -> PipelineState:
    skill = await skill_repository.get(state["skill_id"], state["skill_version_ref"])
    cases = state["_ic_positive_cases"]   # 只对训练集子集做A/B，成本考量见下方说明

    async def run_pair(case: TestCase) -> tuple[ExecutionTrace, ExecutionTrace]:
        loaded, baseline = await asyncio.gather(
            executor_backend.execute(ExecutionRequest(skill=skill, case=case, run_index=0, load_skill=True)),
            executor_backend.execute(ExecutionRequest(skill=skill, case=case, run_index=0, load_skill=False)),
        )
        return loaded, baseline

    pairs = await asyncio.gather(*[run_pair(c) for c in cases])
    trace_ids = []
    for loaded, baseline in pairs:
        await trace_repository.save(loaded); await trace_repository.save(baseline)
        trace_ids += [loaded.trace_id, baseline.trace_id]
    return {**state, "executed_trace_ids": trace_ids, "_ab_pairs": pairs}
```

**成本取舍（本文档的明确决策）**：架构文档模块一要求每用例 3 次冗余执行，但 A/B 对比是"每用例 2 条分支 × 每分支再 3 次"，成本会达到基础评测的 6 倍。本文档决定：**A/B 对比每分支只跑 1 次**（不做 3 次冗余），理由是 A/B 对比关注的是"存在性差异"（有无明显质量/效率差距），而非高精度的触发率统计，容忍单次执行的非确定性噪音；若后续报告显示 A/B 判定本身抖动过大，可在文档 24 落地后通过配置把 `run_count_per_arm` 调高，不需要改动本文档结构。同时 A/B 对比只覆盖 `_ic_positive_cases` 中的**训练集**用例（不含验证集），控制成本，且与本维度自身也有优化闭环（第 8 节）需要训练集这一前提一致。

## 7. `progressive_disclosure_dynamic_probe`：动态渐进式披露探查

```python
async def progressive_disclosure_dynamic_probe(state: PipelineState) -> PipelineState:
    skill = await skill_repository.get(state["skill_id"], state["skill_version_ref"])
    findings = []
    for case in state["_ic_pd_cases"]:
        trace = await executor_backend.execute(ExecutionRequest(skill=skill, case=case, run_index=0))
        await trace_repository.save(trace)
        read_reference_paths = {
            a.action_input.get("path") for a in trace.actions
            if a.action_type == "read_file" and a.action_input.get("path", "").startswith("references/")
        }

        if case.category == TestCaseCategory.PROGRESSIVE_DISCLOSURE_TRIGGER:
            if case.probe_target_reference not in read_reference_paths:
                findings.append(SecurityLikeFinding := f"[漏读] 触发条件满足但未读取 {case.probe_target_reference}，判定为渐进式遗漏(严重)")
        else:  # REGULAR
            if read_reference_paths:
                findings.append(f"[过度抓取] 常规任务擅自读取了 {read_reference_paths}，判定为上下文利用率不达标")

        # Token水位监控：常规任务下 token 消耗应保持低位
        if case.category == TestCaseCategory.PROGRESSIVE_DISCLOSURE_REGULAR and trace.timing.total_tokens > state.get("_baseline_token_watermark", 999999):
            findings.append(f"常规任务 Token 消耗 {trace.timing.total_tokens} 超出基线水位，渐进式设计可能未生效")

    return {**state, "_pd_findings": findings}
```

**这一节点不经过 `judgmental_verdict()`**——判定逻辑本身是对 `ExecutionTrace.actions` 的确定性扫描（是否存在特定 `read_file` 调用），属于文档 08 定义的"量化判定"范畴而非语义裁决，因此本文档在 `judge/rules.py` 注册对应规则（`progressive_disclosure_probe`），把上面的扫描逻辑封装为规则函数，再通过 `judge_agent.quantitative_verdict()` 统一产出 `JudgeVerdict`，与直接手写判断相比保证了裁判记录的一致落库（供报告聚合），本文档伪代码为表达清晰略去了这一层封装，实际实现中按此约定收口。

**"漏读"判定为严重问题（对应 blocking），"过度抓取"判定为非严重问题（Warning）**——理由与文档 12 的阻断策略一致：漏读意味着 Agent 在没有依据的情况下凭幻觉给出答案，是正确性问题；过度抓取是效率问题，不影响正确性，只影响成本，因此严重级别不同，第 8 节报告聚合中会体现这一区分。

## 8. 训练集失败与优化闭环

本维度中，`ROI 判定失败`、`渐进式遗漏（严重）` 两类问题若发生在**训练集**用例上，视为可优化的失败信号，路由进入 `optimizer_loop`（复用文档 09），`retest_fn` 重跑 `ab_comparative_execution` 与 `progressive_disclosure_dynamic_probe` 中对应的子集。控制标定与效率诊断类问题（`trace_efficiency`、`control_calibration`）本文档定为**不触发自动优化闭环**——这两类判定更多是细粒度的"写作风格"建议，自动重写容易引发架构文档反复强调的"过度杀伤力"副作用，交给人工在报告中查看后自行决定是否采纳。

async def finalize_dimension_report(state: PipelineState) -> PipelineState:
    roi_fail = any(...)      # 4.1 verdict fail
    pd_severe = [f for f in state["_pd_findings"] if f.startswith("[漏读]")]
    pd_minor = [f for f in state["_pd_findings"] if f.startswith("[过度抓取]") or "水位" in f]

    await report_generator.record_dimension_result(
        run_id=state["run_id"],
        result=DimensionResult(
            dimension="instruction_control",
            status=JudgeVerdictStatus.FAIL if (roi_fail or pd_severe) else JudgeVerdictStatus.PASS,
            score=None,
            findings=[*([f"ROI判定未通过: 加载Skill无显著增值"] if roi_fail else []), *pd_severe, *pd_minor],

        ),
    )
