## 1. 本文档目标

把文档 21 建立的最小向量能力升级为完整的**混合检索基础设施**（Dense + BM25 + Reranker），并用它驱动三处 Few-shot 闭环：Generator 冷启动时检索历史优质用例、Optimizer 修复时检索过往报错-修复记录、Validator 断言模板的语义检索（正式替换文档 10 的占位实现）。

## 2. 统一混合检索服务

```python
# src/skill_evaluate/memory/hybrid_search.py
class SearchDocument(BaseModel):
    doc_id: str
    collection: str          # "assertion_templates" | "seed_anchors" | "successful_skill_archive" | "optimizer_patch_history"
    text: str                  # 用于BM25索引与展示
    metadata: dict
    embedding: list[float] | None = None   # 写入时可选传入，未传则服务内部调用embedding_client计算


class HybridSearchService:
    async def index(self, doc: SearchDocument) -> None:
        """写入pgvector(embedding列) + Postgres全文检索(tsvector列)，两套索引同一张
        search_documents表内共存(见2.1)，不拆分成两个存储系统——与文档04
        "统一存储PostgreSQL+pgvector"的架构决策一致，本文档只是把该决策落到检索场景。"""

    async def search(self, query: str, collection: str, top_k: int = 5, dense_k: int = 20, bm25_k: int = 20) -> list[SearchDocument]:
        """1. dense_results = pgvector cosine相似度取dense_k条
           2. bm25_results = Postgres ts_rank全文检索取bm25_k条
           3. candidates = dense_results ∪ bm25_results (去重)
           4. reranked = cross_encoder_rerank(query, candidates) 取top_k
           返回按reranker分数排序的最终结果。"""
```

### 2.1 表结构（对文档 21 `case_embeddings` 的姊妹表，独立通用集合表）

```sql
CREATE TABLE search_documents (
    doc_id TEXT NOT NULL,
    collection TEXT NOT NULL,
    text TEXT NOT NULL,
    metadata JSONB NOT NULL DEFAULT '{}',
    embedding vector(1536) NOT NULL,
    text_search tsvector GENERATED ALWAYS AS (to_tsvector('english', text)) STORED,
    created_at TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (collection, doc_id)
);
CREATE INDEX ON search_documents USING ivfflat (embedding vector_cosine_ops);
CREATE INDEX ON search_documents USING gin (text_search);
```

> ⚠️ 文档 21 实现后的修正：`case_embeddings` 实际建的是 **HNSW** 索引（空表上建 ivfflat 召回率极差，
> 本表 `search_documents` 同理建议改 HNSW），且带 `embedding_model` 列；种子锚点**不在** `case_embeddings`
> 里（外键指向 `test_cases`），3.2 节升级时需在 `sync-seed-anchors` 时把锚点索引进本表。升级点是
> `SeedAnchorResolver.resolve_for_skill(skill, count)`。详见 `docs/dev/interfaces/21_generator_trust_and_preflight.md`。

`case_embeddings`（文档 21）与 `search_documents`（本文档）保持独立——前者是"用于坍塌检测的一次性距离计算"，后者是"可检索、带完整元数据的长期记忆库"，两者生命周期和查询模式不同，不强行合并成一张表。

### 3.3 RAG 增强闭环：成功案例归档与 Generator 冷启动检索

```python

async def archive_successful_run(run_id: str) -> None:
    """在文档24主图的收尾节点(全部blocking维度均PASS时)调用。

async def retrieve_few_shot_examples_for_cold_start(new_skill: SkillDefinition, count: int = 5) -> list[dict]:
    """供Generator在为一个全新Skill(历史上从未成功评测过)生成用例时调用，
    检索语义最相近的历史成功案例的"description+对应优质用例"作为few-shot示例，
    与3.2的种子锚点(真实用户Prompt分布)是两种不同性质的先验知识：
    种子锚点解决"用户会怎么问"，这里解决"什么样的测试用例设计模式是被验证过有效的"，
    两者在Generator的Prompt模板中作为两段独立的few-shot来源分别注入，不合并。"""
```

#### 3.3.1 分块策略

`body_markdown` 按 Markdown 标题层级（`##`/`###`）分块，而非固定 Token 窗口滑动切分——这是本文档对架构文档"精心设计文本分块策略，防止破坏指令的上下文连贯性"的具体落实：固定窗口切分极易把一条完整指令的"前提条件"和"具体步骤"切到两个不同 chunk，破坏语义完整性；按标题分块保证每个 chunk 是一个自洽的指令单元（如"错误处理"整节、"参数说明"整节）。过长的单个章节（超过 `chunking.max_chunk_tokens`，默认 800）再退化为按段落二级切分。

### 3.4 Optimizer 修复经验检索

```python
# 对文档09 OptimizerAgent.propose_patch()的增强
async def propose_patch(self, ctx: FailureContext) -> Patch:
    similar_past_patches = await hybrid_search.search(
        query=_summarize_failure(ctx), collection="optimizer_patch_history", top_k=3,
    )
    prompt = render_patch_prompt(ctx, few_shot_patches=similar_past_patches)   # Prompt模板追加few-shot段落
    ...
```

每次 `OptimizationLoop.run()`（文档 09）无论最终是否成功，都在结束时把 `(FailureContext摘要, 最终Patch, 是否通过回归)` 归档进 `collection="optimizer_patch_history"`——**包括失败的尝试**，因为"过去某种补丁方式对某类失败无效"本身也是有价值的负面经验，Prompt 中会区分展示"过往成功修复"与"过往失败尝试(避免重蹈覆辙)"两类 few-shot（`metadata.passed: bool` 字段区分）。这是对文档 09 `propose_patch()` 内部实现的一次增强，不改变其对外接口签名，`OptimizationLoop.run()` 的调用方式不受影响。

## 4. 数据飞轮的触发时机

```
文档24主图收尾 → 判断是否全部blocking维度PASS
      是 → archive_successful_run()（RAG归档，3.3）
      否 → 不归档（避免把有质量问题的Skill污染为"优质范本"）

文档09 OptimizationLoop.run()结束 → 无论成败都归档到optimizer_patch_history（3.4，两种结果都有价值）
```

**只归档"完全通过"的 Skill 作为 RAG 正例**，是本文档的一条明确质量门槛——防止数据飞轮"越转越差"（如果把评测未通过的 Skill 也当作范本存入检索库，后续 Generator/Analyzer 检索到的 few-shot 质量会逐渐劣化）。Optimizer 经验库则相反，成败都存——因为那里的检索目的不是"提供范本"而是"提供经验"，失败经验同样是经验。
