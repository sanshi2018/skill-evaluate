## 1. 本文档目标

组装第 0/1 层的全部公共能力，实现架构文档模块一的完整闭环：生成用例 → 3 次冗余执行 → 计算触发率 → 训练集失败则重写 description 重试 → 验证集终测。这是全项目第一个真正跑得通的评测维度，后续 12~20 各文档在结构上都会参照本文档的组织方式（但不再重复解释公共智能体如何被调用，只强调本维度特有的判定逻辑）。

## 3. `prepare_test_suite`

```python
async def prepare_test_suite(state: PipelineState) -> PipelineState:
    skill = await skill_repository.get(state["skill_id"], state["skill_version_ref"])
    suite = await generator_service.ensure_test_suite(skill)   # 06文档：默认REUSE，尊重手动强制/复用约束
    cases = await test_case_repository.list_by_suite(suite.suite_version_id)
    positive_negative = [c for c in cases if c.category in (TestCaseCategory.POSITIVE, TestCaseCategory.NEGATIVE)]
    return {**state, "active_suite_version_id": suite.suite_version_id, "_trigger_cases": positive_negative}
```

`_trigger_cases` 前缀下划线表示"本维度私有的临时状态"，不属于文档 02 `PipelineState` 正式字段——各维度子图允许在自己的命名空间内扩展私有键，但**不得**读写其他维度的私有键，也不得省略前缀直接复用公共字段名，避免维度间状态串扰（这是本文档为 12~20 建立的约定，后续文档遵循同一模式）。

## 4. `execute_train_cases`：并发执行与冗余聚合

```python
async def execute_train_cases(state: PipelineState) -> PipelineState:
    train_cases = [c for c in state["_trigger_cases"] if c.split == DatasetSplit.TRAIN]
    skill = state["_working_skill"] if "_working_skill" in state else await skill_repository.get(...)

    async def run_one_case(case: TestCase) -> list[ExecutionTrace]:
        requests = [ExecutionRequest(skill=skill, case=case, run_index=i, wall_clock_timeout_s=90)
                    for i in range(3)]
        return await asyncio.gather(*[executor_backend.execute(r) for r in requests])

    results = await asyncio.gather(*[run_one_case(c) for c in train_cases])
    trace_ids = []
    for traces in results:
        for t in traces:
            await trace_repository.save(t)
            trace_ids.append(t.trace_id)
    return {**state, "executed_trace_ids": trace_ids}   # PipelineState reducer 自动 append（文档02 Annotated[list, add]）
```

`executor_backend` 通过依赖注入获得，本节点固定使用 `NODE_BACKEND_ROUTING["trigger_accuracy"] = PLUGGABLE`（文档 03 第 5 节已固定），不做后端判断。

**并发规模控制**：`asyncio.gather` 对全部训练集用例同时发起（每个用例 3 次执行），若训练集用例数量较大可能瞬间创建大量 Hermes 沙箱。本文档约定并发上限由 `ExecutorSettings.max_concurrent_sandboxes`（新增配置字段，追加式扩展文档01 `ExecutorSettings`）通过 `asyncio.Semaphore` 控制，默认值 10，避免压垮 Hermes 沙箱调度器或触发架构文档模块五关注的资源耗尽风险（虽然这里是评测系统自身的资源节流，非被测 Skill 的 DoS 场景，但工程上采用同一防御思路）。

## 5. `judge_train_cases`：触发率量化规则

```python
# src/skill_evaluate/agents/judge/rules.py 中新增注册（本文档对文档08待接入项的实现）
def trigger_rate_positive(inputs: dict) -> JudgeVerdictStatus:
    traces: list[ExecutionTrace] = inputs["traces"]
    rate = sum(1 for t in traces if t.loaded_skill_md) / len(traces)
    return JudgeVerdictStatus.PASS if rate >= 0.5 else JudgeVerdictStatus.FAIL

def trigger_rate_negative(inputs: dict) -> JudgeVerdictStatus:
    traces: list[ExecutionTrace] = inputs["traces"]
    rate = sum(1 for t in traces if t.loaded_skill_md) / len(traces)
    return JudgeVerdictStatus.PASS if rate < 0.5 else JudgeVerdictStatus.FAIL

register_rule("trigger_rate_positive", trigger_rate_positive)
register_rule("trigger_rate_negative", trigger_rate_negative)
```

```python
async def judge_train_cases(state: PipelineState) -> PipelineState:
    verdict_ids, failed_case_ids = [], []
    for case in [c for c in state["_trigger_cases"] if c.split == DatasetSplit.TRAIN]:
        traces = await trace_repository.list_by_case(case.case_id)
        rule = "trigger_rate_positive" if case.category == TestCaseCategory.POSITIVE else "trigger_rate_negative"
        verdict = judge_agent.quantitative_verdict(subject_id=case.case_id, rule_name=rule, inputs={"traces": traces})
        verdict_ids.append(verdict.verdict_id)
        if verdict.status == JudgeVerdictStatus.FAIL:
            failed_case_ids.append(case.case_id)
    return {**state, "judge_verdict_ids": verdict_ids, "_train_failed_case_ids": failed_case_ids}
```

触发率判定属于文档 08 定义的"量化判定"，不需要 LLM，因此本节点不涉及 `criticality` 声明——`Criticality` 只与 `judgmental_verdict()` 相关。

## 7. `optimizer_loop`：接入文档 09 通用闭环

```python
async def optimizer_loop_node(state: PipelineState) -> PipelineState:
    skill = await skill_repository.get(state["skill_id"], state["skill_version_ref"])
    failed_cases = await test_case_repository.get_many(state["_train_failed_case_ids"])
    verdicts = await judge_repository.get_many_by_subjects(state["_train_failed_case_ids"])
    ctx = build_failure_context(skill, failed_cases, verdicts)   # 09文档：强制训练集校验

    async def retest_fn(working_skill: SkillDefinition) -> LoopResult:
        rerun_traces = []
        for case in failed_cases:
            traces = await asyncio.gather(*[
                executor_backend.execute(ExecutionRequest(skill=working_skill, case=case, run_index=i))
                for i in range(3)
            ])
            rerun_traces.append((case, traces))
        still_failing = []
        for case, traces in rerun_traces:
            rule = "trigger_rate_positive" if case.category == TestCaseCategory.POSITIVE else "trigger_rate_negative"
            v = judge_agent.quantitative_verdict(subject_id=case.case_id, rule_name=rule, inputs={"traces": traces})
            if v.status == JudgeVerdictStatus.FAIL:
                still_failing.append(case.case_id)
        return LoopResult(passed=not still_failing, detail=f"{len(still_failing)} 条训练用例仍未通过")

    optimizer = OptimizerAgent()
    patch = await OptimizationLoop(max_retries=3).run(
        run_id=state["run_id"], ctx=ctx, retest_fn=retest_fn, optimizer=optimizer,
    )
    if patch is None:
        # OptimizationLoop 内部已调用 suspend_and_wait，图执行到此挂起，函数不会继续往下走；
        # 此分支仅用于类型完整性说明，实际控制流由 LangGraph 的 interrupt 机制接管。
        raise PipelineSuspended("trigger_accuracy optimizer exceeded max retries")

    working_skill = apply_patch(skill, patch)
    return {**state, "_working_skill": working_skill, "_applied_patch_id": patch.patch_id}
```

**`_working_skill` 的传递**：优化闭环产出的 `working_skill`（打了 description 补丁的内存版本）通过私有状态字段传给后续的 `execute_validation_cases`——验证集必须用**打了补丁之后**的 Skill 定义重跑，否则验证集测的还是旧版本，失去"验证补丁是否真的解决问题且不过拟合"的意义。`execute_train_cases` 节点第 4 节中已包含 `state.get("_working_skill")` 的取值逻辑（供 `optimizer_loop` 内部 `retest_fn` 多轮重试时递进使用同一优先级）。

## 8. `execute_validation_cases` / `judge_validation_cases`

与训练集节点结构一致（复用 `execute_train_cases`/`judge_train_cases` 的实现，仅把 `split` 过滤条件换成 `VALIDATION`，且**验证集判定结果不触发 `optimizer_loop`**——不存在"验证集失败重新路由回训练"的边，这是对"验证集不参与优化，防止过拟合"约束在图结构层面的落实，而不仅是文档 09 的运行时校验）。验证集失败的用例记录在 `_validation_failed_case_ids`，仅用于最终报告展示，不驱动任何重试。

## 9. `finalize_dimension_report`

```python
async def finalize_dimension_report(state: PipelineState) -> PipelineState:
    total_val = len([c for c in state["_trigger_cases"] if c.split == DatasetSplit.VALIDATION])
    failed_val = len(state.get("_validation_failed_case_ids", []))
    score = 1 - (failed_val / total_val) if total_val else None
    await report_generator.record_dimension_result(
        run_id=state["run_id"],
        result=DimensionResult(
            dimension="trigger_accuracy",
            status=JudgeVerdictStatus.PASS if failed_val == 0 else JudgeVerdictStatus.FAIL,
            score=score,
            findings=[f"验证集 {failed_val}/{total_val} 条用例触发判定失败"],
            blocking=True,   # 触发准确度是核心维度，判定失败即阻断（各维度是否 blocking 由该维度文档自行声明）
        ),
    )
    return state
```

`record_dimension_result()` 是本文档对文档 05 待接入项的实现——正式补齐 `ReportGenerator` 上该方法的具体调用方式，其余维度文档（12~20）末尾都会有结构相同的一步。

- 本维度全程使用 `PLUGGABLE` 后端，与文档 03 第 5 节路由表一致，不做覆盖。
