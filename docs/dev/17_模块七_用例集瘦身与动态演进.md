## 4. `redundant_case_pruning`：冗余折叠

```python
async def redundant_case_pruning(state: PipelineState) -> PipelineState:
    cases = await test_case_repository.list_by_categories(state["active_suite_version_id"], [TestCaseCategory.POSITIVE])
    clusters: dict[frozenset[str], list[TestCase]] = defaultdict(list)
    for case in cases:
        if not case.target_capability_ids:
            continue   # 未映射的用例(理论上不应出现,文档16应已全部映射)不参与聚类
        clusters[frozenset(case.target_capability_ids)].append(case)

    demoted_case_ids = []
    for capability_path, members in clusters.items():
        if len(members) <= 1:
            continue
        representative = max(members, key=_representativeness_score)   # 见4.1
        for c in members:
            if c.case_id != representative.case_id:
                c.split = DatasetSplit.COLD   # 降级，不删除，复用文档02已定义的枚举值
                await test_case_repository.save(c)
                demoted_case_ids.append(c.case_id)
    return {**state, "_demoted_case_ids": demoted_case_ids}
```

### 4.1 代表性打分

```python
def _representativeness_score(case: TestCase) -> tuple:
    """选择"最具代表性"的用例留在主干。打分依据（按优先级排序，元组比较）：
    1. prompt长度（更长通常意味着包含更复杂的边界条件/多步骤上下文，符合架构文档
       "保留一个最具代表性(或包含最复杂边界条件)的用例"的表述）
    2. category多样性无关(同cluster内category相同)
    3. 若长度相近(差异<20%)，优先保留split=TRAIN的用例（保证降级不会误伤训练集主力）
    这是启发式而非LLM判断——冗余度本身已经是精确的集合相等关系(capability_path完全一致)，
    "选谁做代表"这一步不需要语义理解，用简单规则即可，避免为这种低风险决策消耗LLM成本。"""
    return (len(case.prompt), case.split == DatasetSplit.TRAIN)
```

> ⚠️ **实现修正（打分与幂等性）**：上面的两元组有两个问题，实际实现是五元组
> `(是否活跃, prompt 长度分桶, 是否 TRAIN, 精确长度, case_id)`：
>
> 1. **缺"是否活跃"这一档时本节点不幂等**。本节点每次评测都会重跑：第二轮若某条
>    已降级的 COLD 用例 prompt 更长，它会被选成代表，于是上一轮留下的那条活跃用例
>    也被降级——**整簇冷掉**，这条能力路径从此没有任何活跃用例覆盖。因此把
>    `split != COLD` 提到最高优先级。（真出现整簇皆 COLD 时，实现会把代表恢复为
>    `TRAIN` 并打 `pruning_representative_restored` 警告日志：`COLD` 在全项目里
>    只有本节点一个生产者，恢复它不构成对人工决策的覆盖。）
> 2. **元组把"长度"排在"是否 TRAIN"之前，第 3 条注释就永远不生效**——长度只要差
>    一个字，TRAIN 偏好就被压过去了。实现按 `_LENGTH_BUCKET_RATIO = 1.2` 做对数
>    分桶来落实"差异 < 20% 视为长度相当"。
>
> 另外补了末位的 `case_id`：仓储返回顺序由数据库决定，没有这一档时 `max()` 返回
> "第一个达到最大值的元素"，同一批数据在两次运行中可能选出不同的代表，于是每次
> 评测都会降级一批不同的用例。

> ⚠️ **实现补充（被降级的验证集用例）**：实现单独统计"其中原属 VALIDATION 的条数"
> 并在报告里点名。验证集是优化闭环（文档 09）判断补丁有没有真的改好的依据，被瘦身
> 缩小时应当有人知情——但这只是提示，不改变"按打分选代表"的规则。

**降级而非直接移出活跃集合**：`DatasetSplit.COLD` 的用例仍然存在于 `test_suite_versions.case_ids` 中，只是文档 11/13/15 等消费方在按 `split` 过滤时天然会跳过 `COLD`（它们只查询 `TRAIN`/`VALIDATION`）。这意味着**本文档不需要修改任何已确认文档的查询逻辑**——`COLD` 状态本身就是文档 02 早已设计好的"惰性过滤"机制，冗余折叠只是这个机制的第一个真实生产者。降级到 `COLD` 的用例按架构文档要求"仅在周末的 Nightly Build 中运行"，该调度策略在文档 24 中落地（本文档只负责打标签，不负责调度）。

## 5. `combinatorial_matrix_analysis`：组合能力覆盖矩阵

```python
async def combinatorial_matrix_analysis(state: PipelineState) -> PipelineState:
    tree = await capability_repository.get(state["capability_tree_id"])
    all_pairs = list(itertools.combinations([n.capability_id for n in tree.nodes], 2))

    covered_pairs = set()
    for case in await test_case_repository.list_by_categories(state["active_suite_version_id"], [TestCaseCategory.POSITIVE]):
        if case.split == DatasetSplit.COLD:
            continue   # 已降级用例不计入组合覆盖统计,避免"靠冗余用例刷组合覆盖率"的悖论
        ids = case.target_capability_ids
        for pair in itertools.combinations(ids, 2):
            covered_pairs.add(frozenset(pair))

    uncovered = [p for p in all_pairs if frozenset(p) not in covered_pairs]
    tree.combinatorial_pairs_covered = [tuple(sorted(p)) for p in covered_pairs]
    await capability_repository.save(tree)
    return {**state, "_uncovered_pairs": uncovered}
```

**组合爆炸的控制**：`itertools.combinations` 是 N² 级别，本文档不做任何近似或采样——架构文档模块七本身没有对组合数量设置上限，但引用模块十"应对方案：放弃全量组合测试"的思路，本文档在 `CoverageSettings` 中新增 `max_capability_pairs_for_matrix`（默认 100，即约 14 个能力节点内的全组合），超过该上限时**只**分析"P0 核心能力两两组合"（此时需要读取文档 18 才有意义的 `tier` 字段——本文档因此在 `tree.nodes` 数量超限时,若 `tier` 仍是文档 16 遗留的占位值,直接退化为全部节点参与组合但按 `max_capability_pairs_for_matrix` 截断取前 N 个,并在报告中注明"未做优先级筛选的截断分析,建议待模块八权重分级完成后重新评估"）。这是本文档在文档 18 尚未提供有意义权重时的过渡策略,不是最终形态。

未覆盖的组合对通过 `CapabilityFocus.combinatorial_pairs` 字段（文档 06 已定义）反向驱动 Generator：

```python
focus = CapabilityFocus(combinatorial_pairs=[(a, b) for a, b in state["_uncovered_pairs"][:settings.coverage.max_combinatorial_patch_per_round]])
await generator_service.incremental_patch(skill, focus=focus, triggered_by="coverage_gap")
```

单轮补生成数量做截断（默认 5 对），避免一次性因为组合缺口过多而生成海量用例，交由后续评测轮次逐步收敛，而不是一次性把测试集撑爆。

> ⚠️ **实现修正（第 5 节的四处）**：
>
> 1. **`triggered_by` 用 `combinatorial_gap` 而不是 `coverage_gap`**。两者都是定向
>    补题，但排查"测试集为什么突然多了 5 条题"时，"单项能力零覆盖"和"两项能力没有
>    被同一条题同时用到"是两个完全不同的原因，值得在审计字段上分得开。该取值在
>    `docs/dev/interfaces/06` 第 2 节的表里已经存在（原先只登记给模块十），本文档
>    是它的首个真实生产者，接口文档已同步。
> 2. **`CapabilityFocus.descriptions` 必填**。伪码只填了 `combinatorial_pairs`，
>    而 `capability_id` 是描述文本的哈希——Prompt 里出现两串哈希，模型无法据此构造
>    出真正同时用到两项能力的场景。同时修好了
>    `agents/generator/prompts/_shared.jinja`：原先组合对那一段也只渲染裸 id
>    （能力 id 与负向约束 id 都已渲染描述，唯独组合对漏了）。
> 3. **只统计仍在能力树上的 id**。用例可能带着指向已消失能力的旧绑定（那正是下一
>    节要处理的孤儿），伪码会把它们写进 `combinatorial_pairs_covered`，库里于是留下
>    一批指向不存在节点的组合对。
> 4. **覆盖率的分母是"分析范围内"的组合对**。截断之后拿全量做分母，得到的数字既不是
>    分析范围的覆盖情况也不是全量的覆盖情况，谁也解释不了。落库的
>    `combinatorial_pairs_covered` 则仍是**全部**已覆盖组合对——那是能力树上的事实
>    记录，不该因为本轮的分析预算而缺一块。
>
> **文档 18 落地后的实际结果（以代码为准）**：排序实现已收敛到
> `nodes/weighted_coverage/priority.py::prioritized_pairs()`，口径改为按
> **`TIER_WEIGHTS` 之和**降序（P0×P0=1.2 最前，P2×P2=0.2 最后），本维度的
> `_prioritized_pairs()` 与 `_tier_ranked()` 都改为委托调用——同一个"优先级怎么定"
> 的问题必须只有一个答案。另一件当初没料到的事：**文档 18 的分级节点排在本维度
> 之后**（16 → 17 → 18），所以同一轮里本节点看到的 tier 仍是占位值、报告里那句
> "未做优先级筛选"不会在接入当轮消失；真实分级落库后**下一轮**才生效，当轮的真实
> 优先级由文档 18 的 `upgrade_combinatorial_priority` 节点重排一次给出。
>
> 以下为本文档原定的过渡实现（保留备查）：
> 截断实现为按 `(tier 之和, 两者中较低的优先级, id 对)` 排序后取前 N 对：文档 18 把
> `tier` 填成真实分级后，"只分析 P0 两两组合"**自动**生效，不需要改代码。判据用
> "树上是否出现了不止一档 tier"而不是"是否等于占位常量"，文档 18 换占位策略也不会
> 让这里悄悄给出错误答案。
>
> `max_combinatorial_patch_per_round` 调成 0 的语义是"只分析、不自动补题"，路由会
> 尊重它并直接跳到孤儿检测——那是测试集人工整理期间的合理运维选择。

## 6. `orphan_case_detection`：能力漂移与弃用侦测

```python
async def orphan_case_detection(state: PipelineState) -> PipelineState:
    tree = await capability_repository.get(state["capability_tree_id"])
    current_ids = {n.capability_id for n in tree.nodes}
    all_cases = await test_case_repository.list_by_categories(state["active_suite_version_id"], [TestCaseCategory.POSITIVE])

    orphans = [c for c in all_cases if c.target_capability_ids and not (set(c.target_capability_ids) & current_ids)]
    for c in orphans:
        await test_case_suggestion_repository.save(TestCaseSuggestion(   # 见6.1新表
            suggestion_id=new_id(), case_id=c.case_id, suggestion_type="orphan_retirement",
            reason=f"绑定能力 {c.target_capability_ids} 已从最新能力树中消失", status="pending",
        ))
    return {**state, "_orphan_case_ids": [c.case_id for c in orphans]}
```

### 6.1 `TestCaseSuggestion`：非阻塞的人工决策队列

```python
class TestCaseSuggestion(BaseModel):
    suggestion_id: str
    case_id: str
    suggestion_type: str   # "orphan_retirement"（本文档）| 未来可扩展其他建议类型
    reason: str
    status: str   # "pending" | "confirmed" | "rejected"
    created_at: datetime
```

> ⚠️ **实现修正（去重与枚举）**：
>
> 1. `suggestion_type` / `status` 落地为 `StrEnum`（`SuggestionType` /
>    `SuggestionStatus`，在 `state/enums.py`），入库仍是同样的字符串。做成枚举是
>    为了让文档 22 的工作台漏掉新类型时会显式地走不进任何分支，而不是静默走进 else。
> 2. 写入用 `save_if_absent()` 而不是 `save()`，靠 `(case_id, suggestion_type)`
>    的**库层唯一约束**去重：同一条孤儿用例连续三次评测都会被检出，人只需要处理
>    一次。放在节点里"先查后写"在多个 run 并发评测同一个 Skill 时必然漏掉。副作用
>    是已被人 `rejected` 的建议不会被重新推回待办——这是期望行为：人已经判断过
>    "这条孤儿用例要留着"。
> 3. 表上**没有** `run_id` 列：建议的生命周期比一次运行长得多，挂上 run_id 会诱使
>    工作台按运行过滤，从而漏掉上周检出、至今没人管的那些。要追溯是哪次运行检出的，
>    看结构化日志事件 `pruning_orphan_case_detected`。
> 4. `reason` 里除了消失的能力 id，还带上用例 prompt 的前 200 字：人要判断的是
>    "该淘汰还是该重新绑定到改名后的能力上"，只给一串哈希等于把判断推回给人去查库。

**这不是一次挂起（不调用 `suspend_and_wait`）**——孤儿用例的存在不影响当前评测运行的正确性（该用例只是"注定会在下次尝试触发已不存在的能力时失败"，但只要没人调用它去测试已删除的能力，它不会主动报错，因为文档 11 等消费方是按 `split` 过滤用例后各自独立执行判定，不会检查能力绑定是否仍然有效）。因此本文档把孤儿检测设计为**异步、非阻塞**的建议队列：写入 `test_case_suggestions` 表（本文档 Alembic 追加），供文档 22 的审查工作台展示待处理建议列表，由人工在评测运行之外的时间批量确认。这与第 4 节"人工确认能力树规模过大"（阻塞性挂起，因为直接影响后续计算是否有意义）在紧急程度上有本质区别，本文档明确区分两种人机协作模式：**阻塞式挂起**用于"不确认就无法继续算下去"的场景，**非阻塞建议队列**用于"可以先继续跑，但需要人类找时间清理"的场景。

## 7. 报告聚合

```python
async def finalize_dimension_report(state: PipelineState) -> PipelineState:
    await report_generator.record_dimension_result(
        run_id=state["run_id"],
        result=DimensionResult(
            dimension="test_suite_health",
            status=JudgeVerdictStatus.PASS,   # 本维度不产生Fail状态——瘦身/漂移都是健康度建议，非质量门禁
            score=len(state["_uncovered_pairs"]) and (1 - len(state["_uncovered_pairs"]) / max(1, len(state["_uncovered_pairs"]) + len(state.get("_covered_pairs", [])))),
            findings=[
                f"折叠冗余用例 {len(state['_demoted_case_ids'])} 条",
                f"未覆盖能力组合 {len(state['_uncovered_pairs'])} 对",
                f"检测到孤儿用例 {len(state['_orphan_case_ids'])} 条，待人工确认",
            ],
            blocking=False,
        ),
    )
    return state
```

本维度**恒定不阻断**——它评估的是测试集自身的健康度而非 Skill 质量，与文档 16 的覆盖率不阻断策略保持一致的逻辑基调。

> ⚠️ **实现修正（第 7 节的三处）**：
>
> 1. **`score` 的表达式有 bug**。`len(uncovered) and (...)` 在没有未覆盖组合对时
>    返回整数 `0`——一份组合覆盖完美的测试集会得到 0 分。实现改为
>    `分析范围内已覆盖组合对 / 分析范围内组合对`（范围为空时取 1.0）。
> 2. **多了一档 `NEEDS_HUMAN_REVIEW`**。它不是门禁而是**故障信号**：只在
>    `_pruning_pair_coverage_ratio` 取不到时出现（主图状态 schema 漏并私有键，或
>    节点被跳过）。判 PASS 等于把整个维度悄悄关掉，而本维度被裁掉的症状是全项目
>    最危险的一个——三个分析节点照常**改库**（用例真的被降级、建议真的落表），
>    报告却写"折叠 0 条 / 未覆盖 0 对 / 孤儿 0 条"，看起来测试集非常健康。
>    `blocking` 在这一档下仍然是 False。
> 3. **findings 里区分"检出条数"与"新增待办条数"**。同一条孤儿用例连续三次评测都
>    会被检出，但待办只在第一次产生；两个数写成一个会让人以为孤儿在不断增加。
>    另外补了三条按需出现的说明：被降级的验证集用例数、截断口径（含"未做优先级
>    筛选"的提示）、组合补题失败的原因。

本维度**不产出任何 `JudgeVerdict`**，也不注册量化规则：`docs/dev/interfaces/08`
第 0 节的铁律管的是"通过/失败的结论"，而本维度没有这样的结论要判。硬造一条"测试集
健康度阈值"规则只会凭空多出一道谁也说不清该定在多少的门禁。
