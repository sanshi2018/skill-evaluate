不仅要看它能否完成任务，还要看它在触发机制、上下文管理以及与智能体交互时的效率。根据提供的官方文档，评测一个 Skill 的优劣主要可以从以下四个核心维度进行：

### 1. 触发准确度与泛化能力 (Triggering Accuracy & Generalization)
一个优秀的 Skill 首先必须在正确的时间被唤醒。评测其触发描述（Description）的优劣有以下标准：

- **准确触发 (Should-trigger 测试):** 评估技能描述是否准确涵盖了该技能的应用范围，确保当用户的复杂或含蓄请求（**如未直接提及技能名称或具体领域**）需要该技能时，智能体能够成功调用它。
    
- **避免误触发 (Should-not-trigger 测试):** 评估技能描述是否足够精确，能够正确排查“近脱靶 (near-misses)”查询。即当用户的请求中**包含共享关键词或概念**，但实际上需要不同功能的处理时，该技能不应被触发。
    
- **泛化能力:** 评估描述是否对特定的测试词汇过度拟合（Overfitting）。优秀的技能描述应该在未见过的验证集（Validation set）上也能保持高通过率，而不仅仅是对训练用例有效。

> [!触发准确度 (Triggering Accuracy)]
> 触发准确度主要评估 Skill 的 `description` 字段是否能引导 Agent 在正确的场景下激活它，而在不相关的场景下保持静默。
> 
> - **正向触发评估 (Should-trigger Queries)**：测试 Skill 是否能在各种真实、复杂的提示词下成功激活。评测的子维度包括：
>     - **表述多样性 (Phrasing)**：是否兼容口语化表述、缩写或拼写错误。
>     - **显式与隐式表达 (Explicitness)**：无论用户是直接点名（如“分析 CSV”）还是只描述了需求（如“帮我把这个数据文件做成图表”），Skill 都能被激活。
>     - **细节与上下文 (Detail)**：无论是简短直接的指令，还是夹杂着文件路径、列名和背景故事的冗长复杂信息，均能正确识别。
>     - **多步骤任务 (Complexity)**：当 Skill 对应的任务被埋藏在多步骤的复杂工作流中时，Agent 是否依然能识别出它的相关性。
> - **反向触发评估 (Should-not-trigger Queries / Near-misses)**：测试 Skill 是否能避开“临界情况（Near-misses）”。例如，对于一个 CSV 分析 Skill，用户如果提出更新 Excel 公式或编写 CSV 导入数据库的脚本等类似但不属于该 Skill 范畴的请求，Skill 不应被错误触发。
> - **触发率 (Trigger Rate)**：由于模型具有随机性，需要将相同的测试提示词运行多次（例如 3 次），计算 Skill 被激活的比例（如以 0.5 作为通过阈值）。
> - **验证通过率 (Validation Pass Rate)**：为了防止描述优化出现“过拟合”，需要将测试集划分为**训练集 (Train set)** 和**验证集 (Validation set)**。最终应以从未参与优化调整的验证集上的通过率，来客观衡量 Skill 触发的泛化能力。

### 2. 上下文利用率与范围界定 (Context Efficiency & Scoping)

Skill 加载后会占用智能体的上下文窗口，因此信息密度的管理至关重要：

- **提供增量知识:** 评估技能是否合理地利用了上下文，即重点关注**智能体缺乏的领域专有程序、特定 API 模式和隐蔽边界情况**，并省略掉智能体已经掌握的常识。
    
- **功能连贯性:** 评估技能是否封装了一个连贯的工作单元。技能范围太窄会导致处理一个任务需加载多个技能（增加开销），太宽泛则会导致难以被精确激活。
    
- **渐进式披露 (Progressive disclosure):** 评估大型技能的内容结构是否合理。优质的技能会将核心指令（`SKILL.md`）保持在 500 行和 5000 个 token 以下，并在确实需要时，才指示智能体去加载单独的参考文件。

> [!**上下文开销与范围划分 (Context Wisely & Scoping)**]
> 评估 Skill 的代码设计是否合理，是否在高效利用 Agent 有限的上下文空间。
> 
> - **Token 及行数限制**：评估 Skill 的主文档 `SKILL.md` 是否精简。官方推荐将其控制在 **500 行**和 **5,000 tokens** 以内。
> - **专有信息占比**：评估 Skill 是否专注于 Agent 不知道的专有约定、特定工具 API 或极端边界情况，并裁剪了 Agent 本身就了解的常识和背景解释。
> - **范围合理性 (Scoping)**：评估 Skill 的功能界定是否清晰。范围过窄会导致任务需要加载多个 Skill，增加冲突风险和系统开销；范围过宽则会导致 Skill 难以被精准触发。

### 3. 指令控制度与实际执行效果 (Instruction Control & Execution)

指令写得好不好，直接影响智能体的工作路径：

- **动态控制粒度:** 评估指令的具体程度是否与任务的脆弱性（Fragility）相匹配。在容忍度高、灵活的任务中应给予智能体自由；在脆弱、容错率低的操作中，则需提供必须严格遵循的步骤。
    
- **提供默认选项:** 评估技能在面对多种工具或方法时，是否给出了明确的默认选择，而不是让智能体在多个选项菜单中自行试错。
    
- **偏向过程指导:** 评估技能是否教会了智能体“如何解决一类问题”的通用过程，而不是仅仅声明某个具体任务的结果该是什么样。
    
- **执行有效性:** 通过观察实际执行轨迹，评估智能体是否会因为指令过于模糊、或包含了不适用于当前任务的说明，从而在无效步骤上浪费时间。

> [!执行与输出质量 (Execution & Output Quality)]
> 评估 Skill 激活后，Agent 是否能够高质量地完成任务，以及该 Skill 是否真正为 Agent 带来了“附加价值”。
> 
> - **执行轨迹分析 (Execution Traces)**：通过阅读 Agent 的实际执行路径（而不仅仅看最终输出）来评估其效率。如果 Agent 浪费时间在无意义的步骤上，通常说明 Skill 指令存在以下问题：
>     - 指令过于模糊，导致 Agent 需要不断试错。
>     - 指令不适用于当前任务，但 Agent 依然盲目跟从。
>     - 提供了太多选项，却没有指定清晰的默认值。
> - **附加价值校验 (Value-add)**：如果 Agent 在完全没有加载该 Skill 的情况下也能很好地完成任务，则说明该 Skill 可能并没有增加价值。
> - **错误与遗漏 (Errors & Misses)**：分析在实际执行中，有哪些指令触发了误报（false positives），遗漏了哪些关键处理，或者有哪些多余步骤可以被裁剪。
> - **测试用例与断言评估 (Test cases, assertions, and grading)**：建立系统化的质量测试流程，通过断言和分级标准来评测输出结果。

> [!控制标定与指令设计 (Control Calibration & Instruction Patterns)]
> 
> 评估 Skill 的指令设计是否符合任务的特征和安全要求。
> 
> - **具体性与脆弱性匹配 (Specificity to Fragility)**：对于脆弱、需要严格一致性的操作（如数据库迁移），评估指令是否足够刚性和具有约束力；对于允许多种路径的柔性任务，评估是否给了 Agent 足够的自由度。
> - **默认值设置**：当有多种工具或方法可用时，评估 Skill 是否提供了首选的默认项，而不是列出等价的选项让 Agent 困惑。
> - **脚本模块化程度 (Bundling Reusable Scripts)**：如果发现 Agent 每次运行都在重复手写逻辑（如数据解析或验证），评估是否需要将这些逻辑固化为 Skill 内部的可重用脚本（放在 `scripts/` 目录下）。

### 4. 脚本接口设计的智能体易用性 (Agentic Usability of Scripts)

如果技能中绑定了可执行脚本（Scripts），脚本的接口设计必须契合智能体的工作模式：

- **非交互性:** 评估脚本是否彻底避免了交互式提示（如密码输入或确认菜单）。因为智能体在非交互式 Shell 中操作，遇到这种提示会导致无限期挂起。
    
- **错误信息的建设性:** 评估脚本抛出的错误是否对智能体有帮助。优秀的错误提示会明确指出哪里出错、期望输入什么以及接下来可以尝试什么。
    
- **结构化输出与分离:** 评估脚本输出是否采用了结构化格式（如 JSON、CSV），并且是否做到了数据分离——即把干净的数据发送到 stdout，将诊断或警告信息发送到 stderr。
    
- **安全性与可预测性:** 评估脚本操作是否具有幂等性、是否提供了安全默认值（如要求明确的 `--force` 标志），以及是否能够限制并处理过大的输出内容以防止上下文截断。
