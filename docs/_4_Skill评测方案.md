Skill 评测方案及详细评测方法

设计一个科学、可量化的 Skill 评测方案，需要从**触发准确度**、**上下文效率**、**实际执行效果**和**脚本智能体易用性**四个核心维度切入。以下是针对各个评测维度的详细评测方法：

---

一、 触发准确度与泛化能力评测 (Triggering Accuracy & Generalization)

评测的核心在于检验 Skill 的描述（`description`）能否在正确的场景下唤醒 Agent，在无关或相似场景下保持静默，且不产生“过拟合”1more_horiz。

1. 详细评测方法：

- **构建高质量测试集 (Eval Queries)**： 准备约 20 个真实、具象的用户提示词（Queries），划分为两类45：
    - **正向触发用例 (Should-trigger, 8~10个)**：
        - **多样性表述**：包含口语化表达、缩写或拼写错误56。
        - **隐式表达**：用户不提及 Skill 名称或专业术语（例如，不提及“CSV分析”），仅描述其业务需求（如“我老板想要一张这个数据文件的图表”）3more_horiz。
        - **细节与复杂度**：混合简短直接的指令，以及包含真实文件路径、列名、个人背景等繁杂上下文的多步骤任务5more_horiz。
    - **反向触发用例 (Should-not-trigger, 8~10个)**：
        - **设计“近脱靶 (Near-misses)”情况**：这些用例需包含与 Skill 相关的关键字，但实际任务不属于该 Skill 的范畴3more_horiz。例如，针对“CSV分析 Skill”，提供“更新 Excel 公式”或“编写 Python 脚本将 CSV 导入 PostgreSQL”等用例69。
- **数据集切分 (Train/Validation Split)**：
    - 将上述测试用例划分为 **训练集 (60%)** 和 **验证集 (40%)**6more_horiz。
    - 仅允许使用训练集的失败案例来指导和修改 Skill 的描述12。
    - 验证集完全不参与优化过程，用于最终测试描述的泛化能力6more_horiz。
- **自动化多轮测试 (Multi-run Trigger Evaluation)**：
    - 由于模型的非确定性行为，每个测试用例需运行 **3 次**613。
    - 通过编写自动化脚本（调用 Agent 客户端并监控其工具调用或执行日志，检测是否加载了该 Skill 的 `SKILL.md`）来进行批量评测7more_horiz。

2. 量化指标与通过标准：

- **触发率 (Trigger Rate)**：一个正向用例在 3 次运行中被唤醒的比例。通过阈值通常设为 $\ge 0.5$（即 3 次里至少唤醒 2 次），反向用例的触发率需 $< 0.5$613。
- **验证通过率 (Validation Pass Rate)**：从未参与优化的验证集中，通过评测的用例占总验证用例的比例。以验证通过率最高的那次描述作为最终版本6more_horiz。

---

二、 上下文利用率与范围界定评测 (Context Efficiency & Scoping)

评测的核心在于检验 Skill 在载入 Agent 上下文窗口时的信息密度及结构合理性1516。

1. 详细评测方法：

- **静态 Token 扫描 (Static Scan)**：
    - 使用工具统计主文档 `SKILL.md` 的行数与 Token 数，检查其是否严格控制在 **500行** 和 **5,000 tokens** 以内1617。
- **“常识剥离度”同行评审 (Omission Audit)**：
    - 审查 `SKILL.md` 中的每一句说明，提出核心问题：**“如果没有这条指令，Agent 会做错吗？”**1718。
    - 凡是解释通用常识（例如“什么是 PDF 格式”、“HTTP 如何工作”）的内容一律裁剪15more_horiz。
    - 确保内容高度聚焦在专有约定、特定 API 模式、团队规范及不易察觉的边界情况（Gotchas）上15more_horiz。
- **连贯性与范围审计 (Scoping Check)**：
    - 评估 Skill 是否封装了一个单一、连贯的工作单元1617。
    - **判定标准**：如果 Agent 完成单个任务需要同时加载多个非常窄的 Skill，说明范围过窄（易导致指令冲突）1617；如果 Skill 包含了互不相关的逻辑（如把“数据库查询”和“数据库备份运维”写入同一个 Skill），则说明范围过宽1617。
- **渐进式披露设计审查 (Progressive Disclosure)**：
    - 检查大型 Skill 是否将参考资料、长错误代码、庞大的配置规范移至 `references/` 目录中1617。
    - 核对 `SKILL.md` 中是否包含具体指令指引 Agent **在何种触发条件**下去按需读取特定的参考文件17。

---

三、 指令控制度与实际执行效果评测 (Instruction Control & Execution)

评测的核心在于检验指令设计是否科学，以及 Agent 实际运行时是否在高效路径上执行1821。

1. 详细评测方法：

- **执行轨迹分析 (Execution Trace Analysis)**：
    - 不能只看最终的输出结果，必须通读 Agent 在评测运行过程中的**完整执行路径**1821。
    - **排查效率损耗**：记录 Agent 是否在无效步骤上浪费了时间（如：因为指令模糊导致不断尝试不同命令；因为指令不适用于当前场景而盲目跟从执行；因为列出太多并列工具选项而陷入选择困难）1821。
- **控制标定校准度评估 (Control Calibration)**：
    - **刚性校验**：对于脆弱且安全性要求高的操作（如数据库迁移），检查指令是否使用极其具体的步骤和绝对不允许修改的命令行序列（刚性控制）17more_horiz。
    - **柔性校验**：对于容错率高、允许自由发挥的任务（如代码审查），检查指令是否倾向于解释“为什么”和提供通用“检查方向”，而非死板规定步骤（柔性控制）1723。
- **过程指导与默认值检查 (Procedures & Defaults)**：
    - 检查 Skill 是否是在教 Agent“如何处理一类问题”（通用规程），而非仅仅声明某个特定任务的静态结果18more_horiz。
    - 检查在面临多种工具选择时，Skill 是否推荐了清晰的默认方案（如：默认推荐使用 `pdfplumber`，仅在扫描件时 fallback 到 OCR），而非给出一个等价的工具菜单22more_horiz。
- **增值对比测试 (Value-add Comparative Test)**：
    - 让 Agent 分别在**加载该 Skill** 与 **完全不加载该 Skill** 的情况下运行相同的复杂任务1718。
    - 如果两者的输出质量和执行效率没有显著区别，证明该 Skill 并没有提供附加价值，需进行针对性修改1718。
- **自验证与流程闭环审查**：
    - 检查 Skill 是否包含针对多步骤任务的显式清单（Checklists）2627。
    - 评估是否建立了**验证反馈循环 (Validation Loops)**（例如：执行编辑 $\rightarrow$ 运行验证脚本检测 $\rightarrow$ 报错则自我修复 $\rightarrow$ 重新验证直到通过）2728。
    - 针对高危、批量或破坏性操作，检查是否包含“计划-验证-执行”的闭环步骤28more_horiz。

---

四、 脚本接口设计的智能体易用性评测 (Agentic Usability of Scripts)

如果 Skill 在 `scripts/` 目录下绑定了可执行脚本，则必须对这些脚本的接口进行针对 Agent 特性的可用性评测23more_horiz。

1. 详细评测方法：

- **非交互性硬性破坏测试 (Non-interactivity Test)**：
    - 在非交互式 Shell 中运行绑定的脚本，故意缺失关键参数33。
    - **通过标准**：脚本绝不能挂起（Hang）或弹出任何交互式 TTY 确认、密码输入等提示33。脚本应立即报错退出，并指引正确的参数使用方法2334。
- **智能体“自学”能力测试 (Help Document Test)**：
    - 运行 `bash scripts/your-script.sh --help` 或 `python scripts/your-script.py --help`34。
    - **通过标准**：输出必须简明扼要地列出所有的参数标志（Flags）、环境变量要求，并提供直观的使用示例，方便 Agent 在运行时自主学习和校准指令23more_horiz。
- **建设性报错测试 (Constructive Error Check)**：
    - 通过故意传递错误的格式或无效的输入值来触发脚本报错35。
    - **通过标准**：脚本报错不能仅仅打印“Error: invalid input”，而必须明确指明：什么出错了、期望输入什么、接下来可以尝试哪些选项（如：“`--format` 必须是 json, csv 或 table 之一，收到: xml”）23more_horiz。
- **输出流分离与结构化测试 (Output Separation Test)**：
    - **通过标准**：
        1. 脚本的纯数据和计算结果必须以易于程序化解析的格式（如 JSON、CSV、TSV）发送到 `stdout`23more_horiz。
        2. 所有的过程日志、警告、错误和诊断信息必须发送到 `stderr`2337。这能保证 Agent 可以干净地用脚本进行管道级联，同时在出错时通过 `stderr` 进行自我纠错2337。
- **安全性、确定性与大小边界测试**：
    - **幂等性测试 (Idempotency)**：连续运行脚本两次，确保第二次运行时会安全优雅地处理“已存在”的状态，而非崩溃2337。
    - **安全保护**：针对破坏性操作，确认脚本是否提供 `--dry-run` 预览功能，或者要求显式传递 `--confirm` / `--force` 标志2337。
    - **大小限制测试**：运行能产生极大输出的任务，检查脚本是否内置了摘要截断或保护机制，以防止返回的内容因过长（如超过 10k~30k 字符）而被 Agent 系统截断，从而造成信息丢失37。
