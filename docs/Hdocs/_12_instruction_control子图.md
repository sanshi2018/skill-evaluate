# instruction_control 子图：指令控制度与执行效果评测（模块三）

> 代码位置：`src/skill_evaluate/nodes/instruction_control/`
> 相关实现：`agents/mini/templates/instruction_control.py`（ROI / 效率两个评审模板）、`agents/generator/prompts/registry.py`（探查用例的出题模板注册）、`state/trace.py`（run_index 号段分配表）
> 接入文档：`docs/dev/interfaces/13_instruction_control_pipeline.md`
> 主图装配：`src/skill_evaluate/graph/main.py`

---

## 1. 一句话说清楚

**把 Skill 真的跑起来，看它到底有没有用、用得好不好。**

模块一回答"这个 Skill 能不能被唤醒"，模块二回答"这份 SKILL.md 写得够不够精简"。这两个都没有回答最根本的问题：**Agent 装上这个 Skill 之后，干活是不是真的变好了？**

instruction_control 子图就是回答这个问题的。它是整套评测里**最贵、最复杂**的维度：要在沙箱里真实执行任务，要做"装 / 不装"两组对照实验，要通读 Agent 的完整执行轨迹。

---

## 2. 设计目的

### 2.1 一个 Skill 被唤醒了，不代表它有用

设想这几种情况，模块一和模块二都发现不了：

| 情况 | 模块一（触发） | 模块二（静态） | 实际问题 |
|---|---|---|---|
| Skill 写的全是模型本来就会的东西 | ✅ 能唤醒 | ✅ 篇幅合规 | 装不装一个样，白占上下文 |
| 指令写得含糊，Agent 反复试命令 | ✅ | ✅ | 能做完，但绕了一大圈 |
| 列了五个等价工具却不说用哪个 | ✅ | ⚠️ 可能被提示 | Agent 在几个方案之间来回切换 |
| 写了"报错时查阅 errors.md"，Agent 就是不去读 | ✅ | ✅ 条件写得很清楚 | Agent 凭记忆瞎答，**答案是错的** |
| 常规任务也把所有参考文件读一遍 | ✅ | ✅ | 渐进式披露形同虚设 |

这些问题只有**真实执行、观察过程**才看得见。

### 2.2 它要检查的四件事

对应架构文档模块三，拆成四个相对独立的子评测：

1. **A/B 增值对比（ROI）**：同一个任务，装 Skill 跑一遍、不装再跑一遍，比较结果质量和执行效率。没有明显差别，说明这个 Skill 没提供价值，应该打回重构。
2. **执行轨迹效率诊断**：通读装了 Skill 的那次执行轨迹，找三种浪费：**反复试错**（指令模糊）、**盲目执行**（指令不适用却照做）、**选择困难**（等价选项太多）。
3. **控制标定**：静态检查指令写得多"死"是否和任务的风险相符。数据库迁移这种高风险操作要给固定步骤；数据分析这类可以探索的任务要给原则和自由度。
4. **渐进式披露动态探查**：模块二只看"加载条件写没写"，这里真的去验证**条件满足时 Agent 读没读、不满足时有没有乱读**。

### 2.3 这四件事为什么放在一个子图里

它们评的是同一件事的不同侧面：**SKILL.md 正文里的指令，在真实执行中起到了什么作用**。

- ROI 看"起没起作用"
- 效率诊断看"起作用的方式对不对"
- 控制标定看"写法本身合不合理"
- 渐进式披露看"条件指令有没有被遵守"

放在一起还有一个现实原因：它们共用同一批用例、同一个执行后端、同一套报告口径。拆成四个维度，报告里会出现四条互相割裂的结论。

### 2.4 核心设计决策

**决策一：该贵的地方贵，该省的地方省。**

| 子评测 | 花费 | 理由 |
|---|---|---|
| ROI 判定 | **3 个裁判独立投票**（CRITICAL） | "这个 Skill 没价值、打回重构"会直接卡住合并，值得花三倍成本换可信度 |
| 效率诊断、控制标定 | 1 个裁判（ROUTINE） | 只是改进建议，不阻断，没必要投票 |
| A/B 执行次数 | 每组**只跑 1 次** | 模块一每条用例跑 3 次，A/B 是两组，跑 3 次就是 6 倍成本。ROI 只关心"有没有明显差距"，不需要精确统计 |
| 渐进式披露判定 | **不用 LLM** | "读没读某个文件"扫一遍执行动作就知道，让模型去数又贵又不准 |

A/B 只跑一次带来的噪音，没有假装不存在：这件事**直接写进了裁判的 Prompt**——"本次每组只跑了一次，差距不明显时判通过"。噪音不应该变成一次打回重构的判决。

**决策二：严重问题阻断，风格问题只提醒。**

| 问题 | 性质 | 阻断合并 | 自动修复 |
|---|---|---|---|
| ROI 不达标 | Skill 没价值 | ✅ | ✅ |
| 漏读参考文件 | **正确性**问题：Agent 凭记忆作答 | ✅ | ✅ |
| 过度读取参考文件 | 成本问题：答案还是对的 | ❌ | ❌ |
| 执行效率低 | 写作风格建议 | ❌ | ❌ |
| 控制标定不匹配 | 写作风格建议 | ❌ | ❌ |

后两类不交给自动修复，是因为让模型自动重写"风格"很容易改过头（架构文档反复提到的"过度杀伤力"），这类修改应该由人看过报告后决定。

**决策三：只拿训练集做优化。**

自动修复闭环只处理训练集上的失败，验证集不参与，避免"针对考题改答案"。代码里有两道关：图结构上验证集的失败根本进不了修复节点；即使进去了，`build_failure_context()` 也会直接报错。

## 3. 在整个评测流程中的位置

### 3.1 主图里的站位

```
pipeline.bootstrap_run（Skill 入库、建运行记录）
        ↓
preflight.*（沙箱指纹、金丝雀探针）
        ↓ 并行扇出
  ├─ context_scoping.*          模块二：静态审查（不依赖用例）
  ├─ script_usability.*         模块四：脚本黑盒
  └─ trigger_accuracy.prepare_test_suite   模块一：生成 / 复用测试集
        ├─ trigger_accuracy.*  执行 → 判定 → 闭环 → 验证 → cross_model.*（模块九）
        └─ security.prepare_adversarial_suite   模块五
              ├─ security.*
              └─┐
   trigger_accuracy.judge_train_cases ─┤  （两者都完成才放行）
                                       ↓
                   ★ instruction_control.prepare_cases（模块三入口）
                          ├─ instruction_control.*（本子图其余节点）
                          └─ coverage.* → pruning.* → weighted_coverage.* → multi_skill.*
        ↓ 所有维度终节点都完成（同步屏障）
finalize.report → finalize.patch_pr → finalize.rag_archive
```

### 3.2 为什么排在这个位置

入口节点等两个前驱都完成才执行，两个前驱各有理由：

| 前驱 | 为什么要等 |
|---|---|
| `security.prepare_adversarial_suite` | 模块一、五、三、六的**准备节点**都会调用 `ensure_test_suite()`。第一次出题时如果两个维度同时调，会各自激活一个新版本用例集，后激活的把先激活的那批用例覆盖掉（数据库层面的丢失更新，不报错）。所以准备节点串行：模块一 → 五 → 三 → 六 |
| `trigger_accuracy.judge_train_cases` | 本子图的 A/B 用的是**模块一的同一批正向用例**，执行轨迹写进同一张表。等模块一判完训练集再开跑最稳妥（号段隔离见 §6.1） |

只串行"准备"这一步，本子图后面的执行、判定仍然和其他维度并行，代价只是几次查询。

### 3.3 与其他模块的关系

```
               提供用例                          复用 A/B 骨架与 ROI 判定
模块一 ──────────────────→ 【模块三】 ←──────────────────── 模块五（安全补丁的功能回归）
（正向训练集）                 │
                              │ 采纳的补丁
                              ↓
                     finalize.patch_pr（与模块一、五的补丁合成一个 PR）
```

- **上游**：Generator（出探查题）、模块一的用例集、执行后端（Hermes 沙箱）、Judge Agent、Optimizer 闭环。
- **下游被复用**：
  - 模块五给 Skill 打了安全补丁后，要确认补丁没把正常功能搞坏。它调用本子图的公开方法 `run_ab_pairs()` / `judge_roi()` 重跑 A/B——一个把路径写死的安全约束不影响 Skill 被唤醒，但会让它处理不了正常任务，只有 ROI 回归能抓到。
  - 模块五的检测器复用了 `format_actions_for_review()`，用来把执行轨迹压缩进 Prompt。
  - 报告节点透传本子图的用例集过期告警；PR 节点读取本子图采纳的补丁。

## 4. 主要业务流程

### 4.1 流程总览

```
prepare_instruction_control_cases           ① 准备两批用例
        │
        ├──────────────────────┬──────────────────────────┐   三条支路并发
        ↓                      ↓                          ↓
ab_comparative_execution   control_calibration_     progressive_disclosure_
  ② A/B 执行 + ROI 判定     static_scan              dynamic_probe
        ↓                   ④ 控制标定（静态）        ⑤ 渐进式披露探查
trace_efficiency_diagnosis
  ③ 效率诊断
        │                      │                          │
        └──────────────────────┴──────────────────────────┘
                               ↓  三条都完成才触发一次
                       collect_findings                  ⑥ 挑出可自动修复的失败
                               │
                 ┌─────────────┴──────────────┐
          有可修复失败                       没有
                 ↓                              │
          optimizer_loop                        │        ⑦ 改写 SKILL.md → 重测
                 └─────────────┬────────────────┘
                               ↓
                   finalize_dimension_report             ⑧ 汇总写报告
```

### 4.2 各节点详解

#### ① `prepare_instruction_control_cases`：准备用例

需要两批用例：

**第一批：A/B 对比用例**
直接复用模块一生成好的**正向用例中的训练集部分**，不重新出题。
- 为什么只要正向：反向用例本来就"不该触发 Skill"，装不装当然没区别，拿去做 A/B 必然误判。
- 为什么只要训练集：A/B 每条用例要跑两遍，成本高；而且本子图的修复闭环只能用训练集。

**第二批：渐进式披露探查用例**
这是本子图专属的两类新题，按"复用优先"原则补齐：用例集里一条这类题都没有时才出题，之后每次运行都复用。

| 题型 | 出题规则 | 期望行为 |
|---|---|---|
| 触发探查题 | **每个写了加载条件的参考文件出一条**，题面精确命中条件（如"我跑的时候报了 KeyError，帮我看看"），且记录这条题瞄准的是哪个文件 | 执行时读了那个文件 |
| 常规对照题 | 固定 3 条，完全在正文范围内 | 不读任何参考文件 |

两类必须成对出现：只有触发题，一个"无脑读所有文件"的 Skill 能满分；只有常规题，一个"从不读文件"的 Skill 能满分。

没有 `references/` 目录的 Skill，两类题都是 0 条，不会发出无意义的出题请求。

#### ② `ab_comparative_execution`：A/B 执行 + ROI 判定

```
对每条用例并发：
   ┌─ 加载 Skill   ──→ 沙箱执行 ──→ 轨迹 A
   └─ 不加载 Skill ──→ 沙箱执行 ──→ 轨迹 B
                          ↓
      ROI 裁判（3 个独立投票）比较：
      · 最终答复的质量
      · 动作步数 / 耗时 / Token
                          ↓
      pass = 有显著增值 ｜ fail = 无附加价值，应打回重构
```

- 两组请求**只有 `load_skill` 一个参数不同**，其余完全一致，否则比出来的差距说不清来源。
- 并发数受 `max_concurrent_sandboxes` 信号量控制：`用例数 × 2` 个沙箱请求不能一次性全打出去。
- 如果三个裁判意见不统一，**不会**把"待人工确认"降级成通过或失败，而是挂起流水线，由审批 guard 生成一张卡片交给人裁决。
- 如果这次判定被抽中做裁判自检（黄金基准盲测），结果不计入本 Skill 的结论，但会在报告里写明"这一项本次没评成"。

#### ③ `trace_efficiency_diagnosis`：效率诊断

唯一有串行依赖的节点：它读的是 ② 刚写入数据库的"加载 Skill"那一组轨迹。

- **只诊断加载组**：问题是"Skill 的指令有没有把 Agent 带偏"，不装 Skill 的那组没有指令可诊断。
- 轨迹交给裁判前会先压缩：超过 40 步时保留首尾各一半（开头看有没有一上来就走错，结尾看收尾时有没有来回折腾）、每步输出截断到 400 字、统一脱敏密钥。整条轨迹原样塞进去会有上百步 × 每步几十 KB，超出上下文且让裁判抓不到重点。
- 裁判分别给出三项结论（反复试错 / 盲目执行 / 选择困难），三项可以同时成立，任一项成立即不通过。

#### ④ `control_calibration_static_scan`：控制标定

复用 Mini Agent 的现成模板 `control_calibration`，整份 SKILL.md 一次判定：

1. 判断任务脆弱性：出错不可逆（fragile）还是可以探索（tolerant）？
2. 判断指令风格：固定步骤（rigid）、原则指引（flexible），还是两者错配（mismatched）？
3. 检查两项：多个等价方案时有没有给默认推荐？高风险任务有没有检查清单或"计划-执行-验证"的闭环？

**评审的是仓库里的原始 SKILL.md**，而不是修复闭环改过的版本。这一项评的是"作者写成了什么样"，拿机器改过的版本去评，报告就和人能打开看到的文件对不上了。

#### ⑤ `progressive_disclosure_dynamic_probe`：渐进式披露探查

```
执行探查题（每条 1 次）
        ↓
扫描执行动作，找出实际读取的参考文件（纯代码）
        ↓
    ┌───────────────┬──────────────────────────────┐
  触发探查题                       常规对照题
    │                                │
  目标文件没读？                   读了任何参考文件？ → [过度抓取]（非严重）
    → [漏读]（严重）               Token 超出同批水位？ → [Token水位]（非严重）
        ↓
按量化规则产出判定（任一发现即判不通过），失败判定写库
```

**怎么判定"读了某个文件"**：只认 Skill 已知的参考文件路径，两种识别方式：
1. `read_file` 等读文件动作的路径参数，按后缀匹配（沙箱里常给绝对路径）；
2. 其他动作（比如 `bash: cat references/errors.md`）的输入里出现已知路径原文。

这样**不会误报**（命中就说明确实提到了那个文件），代价是可能漏报（路径拆成变量拼接就识别不出来）。这是有意的取舍：漏读是严重问题，宁可放过也不能凭猜测指控一份 Skill。

**Token 水位怎么定**：同批常规题 Token 消耗的**中位数 × 1.5**。不用绝对阈值，因为 Token 消耗大部分来自任务本身，换个 Skill 就完全不是一个量级；用中位数不用均值，因为超标的那条本身就在样本里，会把均值拉高。样本少于 3 条时不做这项检查——样本太少，中位数本身就是噪音。

#### ⑥ `collect_findings`：汇合并挑出可修复失败

纯汇总节点，不发请求、不写库。从三条支路的结果里挑出同时满足以下条件的用例：
- 属于**训练集**
- 问题是 **ROI 不达标**或**漏读**

有这样的用例就进 ⑦，否则直接进 ⑧。

> 这个节点是实现时加的，原设计文档里没有。条件路由必须挂在某个节点上，而"要不要修"需要同时看到 A/B 和探查两条支路的结果——挂在任何一条支路上都会漏掉另一条的失败。
>
> 三条支路汇入这里时用的是**多起点边**（`add_edge([三个末端], collect_findings)`）。A/B 支路比另外两条多一个节点，如果分别连三条边，本节点和后续节点会被触发两次，第一次写进报告的结论缺少效率诊断。这个缺陷在主图装配（模块 24）时被发现并修复。

#### ⑦ `optimizer_loop`：自动修复闭环

复用 Optimizer 的通用闭环（最多 3 轮）：

```
失败证据（用例 + 裁判结论）→ Optimizer 生成补丁 → 应用到 SKILL.md 副本
        ↑                                                ↓
        └──────── 仍失败 ←──────── 只重测失败的那几条用例
                                                         ↓
                                                  全部通过 → 采纳补丁
```

- 和模块一用同一个 Optimizer 角色，但**修改方向不同**：模块一改 description（让 Skill 能被唤醒），这里改**正文**。给 Optimizer 的额外说明是：ROI 失败就把容易做错的地方写成可执行的步骤；漏读就把"介绍性的一句话"改成"什么情况下必须先读哪个文件"的指令；不许为了通过判定往正文堆内容（模块二还卡着篇幅）。
- **按题型分别重测**：A/B 失败的重跑两组 + 重判 ROI；漏读的重跑一次 + 重新扫描（不做水位检查，重测样本太少）。
- **重测在节点内部完成，图上没有回边**。连回边意味着每轮都重跑整条支路，3 轮下来成本无法接受，而且图会出现环。
- 3 轮仍不通过时挂起，发审批卡片给人：
  - 人选择采纳候选补丁 → 继续收尾；
  - 人选择放弃 → 抛 `HumanRejectedSuspension`，审批 guard 原样放行，不再重复询问。

#### ⑧ `finalize_dimension_report`：写报告

| 情形 | 状态 | 阻断合并 |
|---|---|---|
| ROI 不达标，或出现漏读 | FAIL | **是** |
| 只有过度抓取 / 水位 / 效率 / 控制标定问题 | NEEDS_HUMAN_REVIEW | 否 |
| 两批用例都为空（什么都没测到） | NEEDS_HUMAN_REVIEW | 否 |
| 其余 | PASS | 否 |

两个值得说明的口径：

- **非阻断问题不报 PASS**。原设计是"只写进 findings，状态仍为 PASS"，那样报告会出现"结论通过，下面却列了一串问题"。改成"待人工确认"后，合并照样不被阻断（阻断只看 `blocking` 字段），但总状态里能看到"有事需要人看一眼"。
- **不给分数**（`score=None`）。四个子评测性质完全不同（语义对比、轨迹诊断、静态审查、确定性扫描），硬凑一个"通过项 / 总项"的平均分没有意义。

报告里还会写明：采纳了哪个补丁（结论是修复后的表现）、用例集是否与当前 SKILL.md 版本不匹配、哪些判定被裁判自检占用。

## 5. 状态与数据流

### 5.1 图状态里放了什么

节点之间只传**摘要和 ID**，执行轨迹和裁判记录本体都在数据库里。

```
prepare ──→ _ic_ab_case_ids ─────────┬─→ ab ──→ _ic_ab_pairs ──→ trace_efficiency ──→ _ic_efficiency_outcomes ─┐
        │                            │      └─→ _ic_roi_outcomes ─────────────────────────────────┬───────────┤
        ├─→ _ic_pd_case_ids ─────────┼─→ probe ──→ _ic_pd_findings ───────────────────────────────┤           │
        └─→ _ic_suite_staleness_warning           calibration ──→ _ic_calibration_outcome ────────┼───────────┤
                                                                                                  ↓           │
                                                              collect ──→ _ic_failed_train_case_ids           │
                                                                                 ↓                            │
                                                  optimizer_loop ──→ _ic_working_skill / _ic_applied_patch_id │
                                                                                 ↓                            ↓
                                                                        finalize_dimension_report ←──────────┘
```

所有私有键都以 `_ic_` 开头。两条硬约定：

1. **主图的状态类型必须包含这些键**。LangGraph 会按节点签名的类型裁剪状态，漏了某个键，对应支路的结论会在收尾时悄悄消失，不报任何错。
2. **不读写其他维度的私有键**。尤其不读模块一的 `_working_skill`：那是 description 补丁，和本子图评的正文不是一回事。

### 5.2 数据库里写了什么

| 表 | 写入内容 |
|---|---|
| `execution_traces` | A/B 两组轨迹、探查轨迹、修复闭环的重测轨迹 |
| `judge_verdicts` / `consensus_results` | ROI（含 3 个投票）、效率、标定的裁判记录；探查只存**失败**的判定 |
| `test_cases` / `test_suite_versions` | 第一次运行时补出的探查题（新版本用例集，旧用例全部继承） |
| `patches` / `patch_application_results` | 修复闭环的候选补丁与重测结果 |
| `dimension_results` | 本维度最终结论 |

裁判记录的 `subject_id` 带前缀区分来源：`roi:<用例>`、`efficiency:<轨迹>`、`pd_probe:<用例>`。同一条正向用例在模块一已经有一条以裸用例 ID 存的触发判定，不加前缀会混在一起。

## 6. 实现中需要特别注意的点

### 6.1 执行轨迹的号段隔离

`execution_traces` 表用 `(用例ID, run_index)` 做唯一键，而本子图跑的是模块一**用过的同一批用例**：

- 模块一对每条用例跑 3 次，`run_index` = 0、1、2；
- 如果 A/B 也从 0 开始编号，会**直接覆盖**模块一的轨迹；
- 即使不覆盖，模块一统计触发率时会把 A/B 中"不加载 Skill"的那组算成"没触发"，一份正常的 Skill 下次运行可能莫名其妙不达标。

解决方式是在 `state/trace.py` 建一张**全局号段分配表**，各维度在自己的号段里编号：

| 号段 | 用途 |
|---|---|
| 0 ~ 2 | 模块一冗余执行 |
| 100 / 101（交错递增至 109） | 模块三 A/B：加载组 / 基线组 |
| 110 | 模块三渐进式披露探查 |
| 140 / 141 | 模块五复用本子图 A/B 做功能回归 |
| 其他 | 模块五、九、十、冷数据回归各自的号段 |

配套措施：
- 模块一的判定只统计自己号段内的轨迹（有专门的回归测试）；
- A/B 每组执行次数上限 5 次（100 起交错编号，到 110 为止），配置超限时节点构造阶段就报错，不会等到运行时悄悄覆盖探查数据；
- 模块五复用 A/B 时通过 `run_index_base` 参数换到自己的号段，否则一次"验证补丁"的重跑会覆盖掉被验证的原始结果。

### 6.2 为什么用静态并行边而不是 `Send`

原设计提到用 LangGraph 的 `Send` API 并发触发三条支路。`Send` 适合"运行时才知道要派生几个同构分支"的场景（比如 map-reduce）；这里是三段**结构不同、数量固定**的逻辑，用静态边的好处是图结构能直接画出来，挂起点也能按节点名精确定位。

### 6.3 出题模板从硬编码改为注册表

原先 Generator 里写死了"正向 / 反向"两套模板。本子图需要新增两个题型，后续模块五、十也要加。改成注册表后，新增题型只需要一个 `.jinja` 文件加一行注册，不再改生成器代码。这项修改同步回写到了 Generator 的设计文档。

## 7. 配置项

| 环境变量 | 默认值 | 作用 |
|---|---|---|
| `SKILLEVAL_INSTRUCTION_CONTROL_RUN_COUNT_PER_ARM` | 1 | A/B 每组执行次数，上限 5。ROI 判定抖动大时调高 |
| `SKILLEVAL_INSTRUCTION_CONTROL_PD_TOKEN_WATERMARK_RATIO` | 0.5 | 常规题 Token 容忍比例（中位数 × 1.5） |
| `SKILLEVAL_INSTRUCTION_CONTROL_PD_WATERMARK_MIN_SAMPLES` | 3 | 样本少于此数不做水位检查 |
| `SKILLEVAL_INSTRUCTION_CONTROL_TRACE_DIGEST_MAX_STEPS` | 40 | 交给效率裁判的最大步数 |
| `SKILLEVAL_INSTRUCTION_CONTROL_TRACE_DIGEST_MAX_OUTPUT_CHARS` | 400 | 每步输出截断长度 |
| `SKILLEVAL_EXECUTOR_MAX_CONCURRENT_SANDBOXES` | 10 | 与模块一共用的沙箱并发上限 |

另有两项在代码里固定：单次执行超时 90 秒（与模块一一致，否则"基线更快"可能只是超时配置不同造成的假象）；后端必须是 `PLUGGABLE`（路由表被改成 `MINI` 时，节点构造阶段直接报错——拿假轨迹判 ROI 比没有结论更危险）。

## 8. 总结

| 问题 | 回答 |
|---|---|
| **这个子图做什么** | 在沙箱里真实执行任务，从 ROI、执行效率、控制标定、渐进式披露四个角度评估 SKILL.md 正文是否真正起作用 |
| **在整个流程里的作用** | 评测体系中唯一回答"装了这个 Skill 是否真的更好"的维度；接在模块一、五的用例准备之后，结论进入最终报告，采纳的补丁进入 PR；A/B 骨架还被模块五用作安全补丁的功能回归闸门 |
| **设计目的** | 发现"能唤醒但没用""能用但低效""写了条件但不遵守"这些静态审查和触发测试都看不到的问题，并把能确定修复的问题自动修掉 |
| **核心取舍** | 重大结论花钱投票，建议类结论单裁判；A/B 只跑一次换成本；能用代码判断的不用 LLM；正确性问题阻断，风格问题交给人 |
