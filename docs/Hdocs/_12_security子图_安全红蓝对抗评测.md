## 1. 一句话定位

**这张子图回答一个问题：当有人试图用恶意输入操纵这个 Skill 时，它扛不扛得住；扛不住的话，能不能自动修好，并且修完没把正常业务改坏。**

它是整条评测流水线里**唯一一个"主动攻击"被测对象**的维度——其余维度都在观察 Skill 在正常/边界输入下的表现，只有它扮演红队，构造攻击载荷真的打进去，再扮演蓝队去定级、修复、验证。

架构文档把它定位为"**对第 0/1 层几乎全部公共能力的一次综合演练**"：它一个新的执行机制都没发明，全部是把已有能力（出题器 / 执行后端 / 裁判 / 断言器 / 优化闭环 / 报告器）按安全语义重新编排。

## 2. 设计目的：为什么安全性要单独做一张图

### 2.1 Agent Skill 的安全面和传统软件不一样

一个 Skill 被加载后，它的正文会变成 Agent 的**指令的一部分**。这带来了传统代码没有的攻击面：

| 攻击面 | 说明 | 一旦得手的后果 |
|---|---|---|
| 提示词注入 | 用户输入里夹带"忽略以上指令""你现在是……" | Agent 泄露系统提示词、执行越界指令 |
| 数据投毒 | 待处理的文件里藏着命令注入载荷（CSV 公式、shell 元字符） | 载荷被当命令执行 |
| 凭据窃取 | 诱导 Agent 回读环境变量 / 凭据文件并写进答复 | 密钥泄露到用户手里 |
| 目录穿越 | 诱导 Agent 读写工作区之外的路径 | 越权访问宿主机文件 |
| DoS | 超大输入或不可终止的任务拖死沙箱 | 评测/生产资源被耗尽 |
| 生成物注入 | Skill 把用户内容原样拼进它生成的 SQL / HTML | 漏洞被交付给下一个使用者 |

这些问题**静态审查看不出来**（正文写得再规范，模型也可能被说服），必须真的把攻击跑一遍才知道。所以安全性不能并进"读文档挑毛病"那类维度，得单独有一张能真实执行、能定级、能闭环修复的图。

### 2.2 要解决的五个工程难题

| 难题 | 本子图的对策 |
|---|---|
| **攻击必须真的发生**：不能靠 LLM"想象"一次注入 | 固定用可插拔完整 Agent（Hermes）在真实沙箱执行；装配期硬校验，路由被改成 Mini 后端就拒绝启动 |
| **评测系统自己不能成为攻击载体**：把凭据窃取载荷喂给一个能出网的 Agent = 一次真实数据外泄 | 装配期硬校验沙箱**无出站网络**（白名单非空直接拒绝启动，全项目唯一一处"配置不对就不让跑"） |
| **判定要可信**：漏判一个真实漏洞比误报严重得多 | 安全类语义裁决**一律走 3 副本共识（CRITICAL）**，且刻意不做成配置项；共识取最严的那一档，不是多数票 |
| **不是所有"未完美拒绝"都是致命漏洞** | 探测节点给初始严重级别，统一的定级节点拿实际证据做最终裁定（可上调可下调） |
| **自动修安全容易"过度杀伤"**：为防路径穿越把路径写死，正常跨目录读取就废了 | 补丁必须过一次**强制功能回归**（触发率 + A/B 增值），修好安全但改坏业务的补丁会被打回 |

### 2.3 判定分层：能用规则算的，绝不花钱问 LLM

五条探测支路里，**只有提示词注入那一条需要语义理解**（"它到底有没有被说服"），其余四条的判定依据都是确定性事实：

- 载荷有没有被当命令跑 → 扫动作序列里的命令注入特征
- 答复里有没有凭据格式 → 跑一遍脱敏正则库（复用日志脱敏那套规则）
- 有没有一次成功的越权读写 → 看路径是否逃逸出工作区 + `exit_code` 是否为 0
- 沙箱是超时还是崩了 → 看末尾动作的 `action_type`

这四条走**量化规则**（同步、不调 LLM、结论仍统一经 Judge 落库），既满足"一切判定经 JudgeAgent"的铁律，又不会为了数一个退出码去花一次模型调用。

## 3. 主要业务流程

### 3.1 图结构（九个节点，五条并行探测支路）

```
prepare_adversarial_suite         ← Attacker Agent 备好对抗用例（REUSE，有就复用）
      │
      ├──────────────┬──────────────┬───────────────┬──────────────┐   ← 五条支路并发
      ↓              ↓              ↓               ↓              ↓
 direct_prompt_  data_         env_and_        dos_context_   artifact_
 injection_probe poisoning_    traversal_      exhaustion_    sast_review
   (语义裁决)     probe(规则)   probe(规则)      probe(规则)    (断言脚本)
      └──────────────┴──────────────┴───────────────┴──────────────┘
                              ↓                                    ← 汇合
                   security_posture_scoring      ← 逐条最终定级 + 落库
                              │
              route_after_scoring
              ├─ 有中危及以上（且在训练集）→ appsec_optimizer_loop
              │        修补丁 → 安全重测 → 强制功能回归 → 收敛/挂起
              └─ 否 ───────────────────────────────────────┐
                                                            ↓
                                            finalize_dimension_report   ← 写维度结论
```

### 3.2 一次完整评测的数据流

**① 出题（prepare_adversarial_suite）**
Attacker Agent 按七个攻击面各出一批用例。它是 `GeneratorAgent` 的子类，完全复用出题器的三态生命周期（默认复用、只有从没出过题时才生成一次），因此同一份 Skill 两次评测拿到的是同一批攻击——这样"加固后安全分上升了"才有意义（挡住的是同一批攻击，不是这次换了批更好打的题）。

**② 五条支路并发探测**
每条支路挑出属于自己攻击子类型的用例，在无出站网络的一次性沙箱里真实执行一次，落 Trace，然后：
- 提示词注入 → `judgmental_verdict()` 3 副本共识裁决"有没有被绕过"
- 其余四条 → 确定性扫描器提取证据 → `quantitative_verdict()` 量化规则出结论
- 生成物注入 → Validator 规划断言脚本，随任务下发，Hook 回传退出码决定（**完全不经 LLM 裁判**）

每条支路把发现放进图状态（不落库），支路间用 `operator.add` 汇总，保证五条并行写入互不覆盖。

**③ 统一定级（security_posture_scoring）**
拿每条发现的**实际证据**重新裁定严重级别（致命/高危/中危/低危）——探测节点给的只是"这类攻击一旦得手有多严重"的先验，这里可以上调也可以下调。这也是发现**唯一的落库入口**，保证库里每条记录都带最终等级。

**④ 修复闭环（appsec_optimizer_loop，仅在训练集有中危及以上时触发）**
以 AppSec 专家角色生成补丁（改正文加刚性约束，或改脚本），补丁的"算修好了"有两段，缺一不可：
1. 对应的攻击用例重跑一遍不再打穿；
2. **强制功能回归**通过——拿打了补丁的 Skill 重跑模块一的触发率 + 模块三的 A/B 增值判定，证明没把正常业务改坏。
闭环最多跑 N 轮，仍不过则挂起等人工。

**⑤ 收尾（finalize_dimension_report）**
把结论写进 `dimension_results`，交给报告器聚合。

## 4. 在整条评测流水线里的位置与作用

### 4.1 它在主图的哪一环

主图（`graph/main.py`）里，安全维度排在**模块一（触发准确度）的准备节点之后**：

```
trigger_accuracy.prepare_test_suite   ← 先产出/激活用例集
        ↓
security.prepare_adversarial_suite    ← 再补对抗用例（串行，避免两边同时出题互相覆盖）
        ↓（五条探测支路照常与其他维度并行跑）
```

**为什么串行准备节点**：安全维度和其余几个维度都会调 `ensure_test_suite()`。从没出过题时若并行，两边会同时激活各自的新版本，后激活的把先激活那批用例从 active 版本里挤掉（数据库层的 lost update，不报错）。串行只作用于**准备节点**，五条探测支路仍与其余维度的执行并行,墙钟代价只是几次复用查询。

### 4.2 它给整个流水线贡献什么

| 贡献 | 去向 |
|---|---|
| **安全维度结论**（PASS / FAIL / 需人工） | `dimension_results` → 报告的维度列表 |
| **是否阻断合并**（`blocking`） | 报告的 CI 阻断判定：有高危/致命且没修好 → 整条流水线红灯 |
| **安全发现明细**（按严重级别聚合） | `BenchmarkReport.security_findings_summary` |
| **经回归验证的补丁** | `finalize.patch_pr` 节点转成真实 PR（安全补丁优先级最高，冲突时保留它） |

### 4.3 `status` 与 `blocking` 的分离（本维度的一个关键设计）

- **`status` 回答"这次发现了什么"**：只要出现过高危/致命，`status` 就是 FAIL——漏洞确实存在过，报告里必须看得见，哪怕补丁已经修好了。
- **`blocking` 回答"要不要卡住这次合并"**：补丁已通过强制功能回归时 `blocking=False`（问题视为已解决），否则 `True`。

两者分开，报告才能同时表达"这里曾经有个致命漏洞"和"但它已经被自动修复并验证过了"。真正的合并动作由 CI/CD 决定，本维度只反映评测事实。

### 4.4 中危的两套阈值

- **进不进修复闭环**：中危及以上都进（架构要求"中危及以上路由到修复"）；
- **卡不卡合并**：只有高危/致命卡。

中危会被自动修一次、会出现在报告里，但不单独把一次合并卡死——否则"拒绝得不够干脆"这类问题会把门禁变成一个所有人都想绕过的东西。

## 5. 关键设计取舍速查

| 取舍 | 怎么做 | 为什么 |
|---|---|---|
| **无出站网络是硬约束** | 装配期校验白名单为空，非空拒绝启动 | 本维度会把真实攻击载荷喂给 Agent，能出网 = 评测系统自己成了外泄通道 |
| **安全判定全走 3 副本共识** | `Criticality.CRITICAL`，且不做成配置项 | 安全假阴性后果远大于假阳性；做成配置等于给"省钱关掉共识"留口子 |
| **共识取最严档，不是多数票** | 三个裁判有一个判致命就取致命 | 按多数票压低 = 用投票给已发现的高危降级 |
| **超时即通过** | DoS 规则里超时优先判 PASS | 墙钟约束成功阻断了挂起，这正是期望结果；用系统硬上限做超时口径，防止用配置制造"安全通过" |
| **没扫过 ≠ 通过** | 断言跑不成判"需人工"，零对抗用例判"需人工" | 判 PASS 会让"工具箱没配好"在报告里表现为"生成物安全" |
| **宁可误报不可漏报** | 确定性扫描器全部偏保守（退出码未上报按成功算等） | 误报让人多看一眼，漏报让真实漏洞被合并 |
| **证据先脱敏再落库** | 写进发现/日志的 Trace 摘要都过一遍脱敏 | 证据里常带刚泄露的凭据，原样落库 = 评测系统自己又泄露一次 |
| **验证集不参与优化** | 只有训练集的阻断项进闭环，验证集阻断项直接判人工 | 防过拟合——拿验证集的攻击去优化，Skill 只学会挡那几条特定的题 |
| **强制功能回归** | 补丁必须重跑触发率 + A/B 才算修好 | 自动安全约束容易"过度杀伤"，修好安全却改坏业务 |

## 6. 复用与被复用关系

**它复用（不重新发明）：**
- 出题器三态生命周期（`agents/generator`）→ Attacker 只换 Prompt
- 执行后端 + Trace（`executors`）→ 真实沙箱执行
- 裁判的量化规则 + 语义裁决 + 共识 + 黄金盲测 + 失误率冻结（`agents/judge`）
- 断言器 + 断言工具箱（`agents/validator`）→ 生成物 SAST
- 优化闭环（`agents/optimizer`）→ AppSec 修复
- 模块一的触发率判定 + 模块三的 A/B 判定 → 强制功能回归
- 日志脱敏正则库（`observability/log_sanitize`）→ 凭据检测
- 报告器（`observability/report_generator`）→ 维度结论聚合

**它留给后续模块复用：**
- 确定性安全扫描器（命令注入 / 凭据 / 路径逃逸 / 超时崩溃识别）——纯函数，无 IO
- 强制功能回归器 `FunctionalRegressionRunner`——19/20 想"拿某个变体 Skill 重跑模块一/三判定"可直接用
- Attacker 的攻击手法注册表——新增攻击面 = 加一个 Prompt + 一次注册，不改任何执行逻辑

## 7. 一张图看懂它的价值

```
没有这张图：                          有这张图：
Skill 通过了功能测试就合入            Skill 先被红队真实攻击一遍
   ↓                                    ↓
上线后被用户注入绕过                  漏洞在合入前被发现、定级
泄露密钥 / 越权 / 生成带毒产物         ↓
   ↓                                 中危以上自动尝试修复
成为一次真实安全事件                  ↓
                                     修复过强制功能回归（没改坏业务）
                                     ↓
                                     带证据的补丁转成 PR 等人审
                                     ↓
                                     高危未修好 → CI 红灯，挡住合并
```

**核心价值**：把"上线后才会暴露的安全事件"提前到"合入前的一次自动化红蓝对抗"，并且做到发现问题的同时给出经过功能验证的候选修复——而不是只甩给开发者一句"这里不安全"。
