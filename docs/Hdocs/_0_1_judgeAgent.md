元评测 == 评测评测机自身的能力

可以用“考试阅卷”来理解：
- 三副本共识：让三位老师独立阅卷，看评分是否稳定、扣分点是否相同。
- 黄金基准盲测：偷偷放入一道已经由专家确定答案的题，看老师到底判得对不对。
- 冻结机制：如果老师连续错判，就暂停他的阅卷资格。
- 人工复核：三位老师意见不一致时，交给教研组裁定。

它验证三方面。
1. 判决稳定性
同一份材料，从不同审查视角、温度或模型进行复核，结论是否仍然一致。
例如同一个执行轨迹：
- 证据充分性视角判 FAIL；
- 反例搜索视角判 FAIL；
- 内部一致性视角也判 FAIL。
说明这个判决对提示词的小幅扰动比较稳定，不太像一次偶然的 LLM 输出。
如果稍微换个视角就从 PASS 变成 FAIL，说明裁判本身不稳定，这时不应让它自动阻断 CI。
2. 证据归因能力
不仅检查三位裁判是否都说 FAIL，还检查它们是不是因为同一个核心行为而判 FAIL。
比如：
裁判 A：因为 step:7 泄露密钥，所以 FAIL
裁判 B：因为 step:7 泄露密钥，所以 FAIL
裁判 C：因为 step:7 泄露密钥，所以 FAIL
这说明裁判系统能稳定地把结论归因到相同证据。
反过来，如果三位裁判虽然都判 FAIL，但分别引用 step:2、step:8、step:15，说明这个 FAIL 的依据并不稳定，可能存在：
- 模型抓错重点；
- Prompt 标准不明确；
- Trace 信息不足；
- 多个问题被混在同一个判定中；
- 模型只是先决定 FAIL，再随便找理由。
因此 [step:N] 实际评测的是 Judge 的“证据落点稳定性”。
3. 不确定性识别和安全降级能力
评测系统不仅要会给 PASS/FAIL，还必须知道什么时候“不应该自动下结论”。
当三份判决不一致时，系统输出：
NEEDS_HUMAN_REVIEW
这测试的是评测系统有没有可靠的拒判和升级机制。
对于 CI/CD 场景尤其重要：
- 错误 PASS 会放过真实问题；
- 错误 FAIL 会错误阻断发布；
- 无法确定时升级人工，通常比强行二选一更安全。

---
[step:N] 有什么用？

STEP_CITATION_RULE = (
    "本次判定会进入高置信度复核流程。若你的依据来自执行 Trace 的某个步骤，"
    "请在 reasoning 中用 `[step:N]` 格式标注（N 为该步骤的 step_id），"
    "可标注多个。判定依据不涉及任何 Trace 步骤时（例如纯静态文本审查），"
    "不要编造 step_id。"
)

程序不理解三位质检员写了什么大道理，它只检查两把锁：
第一把锁：三个人的结论是否完全相同？
第二把锁：三个人是否至少引用了同一个关键证据？
只有两把锁都打开，才算达成共识。
[step:N] 到底有什么作用
LLM 的 reasoning 是自然语言，例如：
用户先读取了配置文件，随后把密钥发送到了外部服务器，因此存在泄露风险。

人能看懂，但程序很难稳定判断三份话术不同的说明是不是在说同一件事。
所以系统要求 LLM 在文字里插入一个机器可识别的“证据坐标”：
用户在 [step:7] 把密钥发送到了外部服务器，因此判定失败。

[step:7] 就像：
- 监控录像的“第 7 个画面”；
- 法庭卷宗的“第 7 号证据”；
- 足球比赛录像的“第 7 个关键事件”；
- 快递轨迹里的“第 7 条物流记录”。
它把模糊的自然语言，变成了程序可以机械比较的编号。
程序会从三份 reasoning 中抽出编号：
裁判 A 引用：{7}
裁判 B 引用：{7, 9}
裁判 C 引用：{7}
三个集合都有 7，因此证据节点一致。
重点是：[step:N] 不是让模型的判断自动变正确，而是让模型说明“你具体依据哪一步”，从而让程序能够检查三位裁判是否真的在讨论同一件事。

案例一：三位安检员都抓住了同一个问题
假设我们检查一名旅客是否违规携带液体，行为记录是：
step:1 旅客进入机场
step:2 旅客办理登机牌
step:3 安检机发现一个 2 升水瓶
step:4 旅客接受人工检查
三位裁判分别给出：
裁判 A：FAIL
理由：在 [step:3] 发现超量液体。

裁判 B：FAIL
理由：安检机于 [step:3] 检出 2 升水瓶。

裁判 C：FAIL
理由：依据 [step:3]，携带液体超过限制。
程序先检查状态：
{FAIL, FAIL, FAIL}
只有一种状态，因此第一把锁通过。
然后提取证据编号：
A = {3}
B = {3}
C = {3}
三者交集是：
{3}
第二把锁也通过。
最终结果：
consensus_reached = true
final_status = FAIL
这里程序并没有理解“水瓶”“安检”或“液体限制”。它只是确定地算出：
状态完全一致，并且引用步骤存在交集。
案例二：结论相同，但其实说的不是同一件事
还是检查同一名旅客：
step:2 登机牌姓名似乎有拼写差异
step:3 安检机发现 2 升水瓶
step:8 旅客在登机口与工作人员争吵
三位裁判给出：
裁判 A：FAIL
理由：登机牌信息有问题，见 [step:2]。

裁判 B：FAIL
理由：携带超量液体，见 [step:3]。

裁判 C：FAIL
理由：扰乱登机秩序，见 [step:8]。
状态检查：
{FAIL, FAIL, FAIL}
